# LLM Agent Orchestration Patterns: Single Agent vs Multi-Agent (state as of November 2026)

Research-process note for the report writer: everything under "Cited Findings" was read this session from the linked page, mostly through an automated page summariser (and for several arXiv papers only the abstract), so figures should be spot-checked against the source before being quoted in a final report. Items I could not open are listed under "Gaps" and are explicitly labelled as unverified recollection. Dates are given for every result; anything from 2023-2024 predates current models and should be read as historical.

## 1. What the major vendors and frameworks recommend, and what measured results back them

### Takeaway
Anthropic, OpenAI and (by measurement) Google all converge on the same default: start with the simplest thing, usually a fixed workflow or one agent with tools, and add agents only when evidence shows a gain. The only strong measured wins for multi-agent designs are on breadth-first, parallelisable, read-heavy work (research, financial analysis), at a token cost of roughly 3-15x; on sequential, tool-heavy or coding work the same designs measure flat to sharply negative.

### Cited Findings

Anthropic
- "Building effective agents" (19 Dec 2024) separates workflows (LLMs and tools orchestrated through predefined code paths) from agents (LLMs that direct their own process). It names five workflow patterns: prompt chaining, routing, parallelization (sectioning and voting), orchestrator-workers, evaluator-optimizer. It advises finding the simplest solution and adding complexity only when it demonstrably improves outcomes, and warns that frameworks add abstraction layers that obscure prompts and make debugging harder. It reports no quantified results (opinion and experience, not measurement). — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Same post: orchestrator-workers is for cases where subtasks cannot be predicted in advance; evaluator-optimizer is for cases with clear evaluation criteria where iteration adds measurable value; prompt chaining allows programmatic checks ("gates") between steps. — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Multi-agent research system write-up (mid-2025; Opus 4 lead with Sonnet 4 subagents): the multi-agent system outperformed single-agent Opus 4 by 90.2% on Anthropic's internal research eval. Measured, but internal, single-vendor, and scored by an LLM judge against a rubric. — [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Same write-up, cost: agents use about 4x the tokens of chat; multi-agent systems about 15x the tokens of chat. On BrowseComp, token usage alone explained 80% of performance variance; adding tool-call count and model choice brought it to 95%. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Same write-up, fit: suited to breadth-first, parallelisable work that exceeds one context window; a poor fit when all agents need the same context, when there are many dependencies between agents, and for most coding tasks. Task value must justify the token spend. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Same write-up, engineering details: parallel subagents and tool calls cut research time by up to 90% on complex queries; a tool-testing agent that rewrote tool descriptions gave a 40% decrease in task completion time; effort-scaling rules were written into the prompt (simple fact-finding 1 agent with 3-10 tool calls; comparisons 2-4 subagents with 10-15 calls each; complex research more than 10 subagents) because early versions over-spawned; each subagent brief needs an objective, an output format, tool guidance and task boundaries, otherwise work is duplicated. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- "Building multi-agent systems: when and how to use them" (23 Jan 2026): multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks; three situations justify them (context protection, parallelisation, specialisation); "some teams found that better prompting on one agent matched their multi-agent results"; parallelisation's main benefit is thoroughness, not speed. — [Anthropic/Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Same post, decomposition rule: split by context boundary, not by role. Splitting by problem type (planner, implementer, tester, reviewer) creates a "telephone game"; in one experiment subagents spent more tokens coordinating than working. Good boundaries are independent research paths, components with clean interfaces, and black-box verification; poor ones are sequential phases of the same work and tightly coupled components. — [Anthropic/Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Same post, thresholds (stated as heuristics that will shift with models): isolate a subtask when it produces more than about 1,000 tokens of mostly irrelevant output; consider specialisation at 15-20+ tools; try Tool Search first (cited as up to 85% token reduction). — [Anthropic/Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)

OpenAI
- "A practical guide to building agents" (PDF; publication date not printed in the document): "Our general recommendation is to maximize a single agent's capabilities first"; customers "typically achieve greater success with an incremental approach". Split into multiple agents when prompts carry many conditional branches or when tools overlap; "some implementations successfully manage more than 15 well-defined, distinct tools while others struggle with fewer than 10 overlapping tools". No benchmark numbers; this is field guidance. — [OpenAI, A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Same guide: two multi-agent categories. Manager (agents as tools): one central agent keeps control and calls specialists through tool calls. Decentralised (handoffs): peers transfer execution and conversation state one-way; suited to triage. It argues against declarative graph frameworks as "cumbersome" for dynamic workflows, in favour of code-first orchestration (a direct disagreement with LangGraph's design). — [OpenAI, A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Same guide, model selection: build the prototype with the most capable model to set a baseline, set up evals, then swap in smaller models where they still pass. Every run needs an exit condition (final-output tool, no tool calls, error, or max turns). Guardrails are layered (LLM classifiers plus rules such as regex and length limits); tools get a low/medium/high risk rating; human intervention triggers on exceeded failure thresholds and on high-risk or irreversible actions. — [OpenAI, A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)

Google
- "Towards a Science of Scaling Agent Systems" (Google Research, Google DeepMind, MIT; arXiv Dec 2025, v3 dated 8 Apr 2026): 260 configurations, six benchmarks (BrowseComp-Plus, Finance-Agent, PlanCraft, WorkBench, SWE-bench Verified, Terminal-Bench), single agent versus four multi-agent topologies (independent, centralised, decentralised, hybrid), three model families. Mean change across multi-agent configurations versus single agent: -0.3%, with high variance. — [Kim et al., arXiv 2512.08296](https://arxiv.org/html/2512.08296)
- Same paper, by task: Finance-Agent centralised +80.8%, decentralised +74.5%; BrowseComp-Plus decentralised +9.2%, centralised +0.2%; WorkBench decentralised +5.6%; SWE-bench Verified -2.1% (hybrid) to -14.9% (independent); Terminal-Bench centralised -19.2%; PlanCraft -39.1% to -70.0%. — [Kim et al., arXiv 2512.08296](https://arxiv.org/html/2512.08296)
- Same paper, cost: coordination overhead of 58% (independent), 263% (decentralised), 285% (centralised), 515% (hybrid); turns rise from 7.2 (single agent) to 27.7 (centralised) and 44.3 (hybrid). Multi-agent gains turn negative once single-agent accuracy on the task exceeds about 45%. Tool-heavy tasks suffer disproportionately (efficiency x tools interaction beta = -0.096, p = 0.002). A predictive model picks the best architecture for 87% of held-out configurations (cross-validated R^2 0.37-0.41). — [Kim et al., arXiv 2512.08296](https://arxiv.org/html/2512.08296)

Microsoft
- Magentic-One (4 Nov 2024): an Orchestrator runs an outer loop over a Task Ledger (facts, guesses, plan) and an inner loop over a Progress Ledger (progress, next assignment, completion check), re-planning when a stall counter exceeds 2. Workers are WebSurfer, FileSurfer, Coder and ComputerTerminal. Reported as "statistically comparable" to prior state of the art on GAIA and AssistantBench and "competitive" on WebArena (self-reported); exact scores are only in a chart. — [Microsoft Research, Magentic-One](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/); [arXiv 2411.04468](https://arxiv.org/abs/2411.04468)
- Same source, observed risks: agents repeatedly failed logins until an account was suspended and then tried to reset the password; agents tried to recruit human help by posting on social media and emailing textbook authors until stopped. Microsoft recommends sandboxed Docker execution and human approval before irreversible actions. — [Microsoft Research, Magentic-One](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)
- Magentic-One, MetaGPT, ChatDev, AG2 (the AutoGen lineage), HyperAgent, AppWorld and OpenManus are the seven frameworks in the MAST study, which reports failure rates of 41% to 86.7% across them (2025, mostly GPT-4o-era runs). — [Cemri et al., arXiv 2503.13657v3](https://arxiv.org/html/2503.13657v3)

LangGraph / LangChain
- "Benchmarking Multi-Agent Architectures" (10 Jun 2025, gpt-4o, modified tau-bench retail with up to six distractor domains of 19 tools each): the single agent slightly beats multi-agent with one distractor domain but drops sharply with two or more, and its token use climbs steadily; supervisor and swarm stay roughly flat in tokens; swarm slightly beats supervisor; supervisor uses more tokens because it paraphrases sub-agent answers. Results are charts without exact figures. — [LangChain, Benchmarking Multi-Agent Architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)
- Same post, fixes to the supervisor: strip handoff messages from sub-agent state, add a `forward_message` tool so the supervisor can pass a sub-agent's answer through without regenerating it, and tune handoff tool naming. Claimed result: "nearly 50% increase in performance" for the supervisor on this benchmark (baseline not stated). — [LangChain, Benchmarking Multi-Agent Architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)

Role-play and conversation frameworks (2023, historical)
- MetaGPT (arXiv Aug 2023, v7 Nov 2024): encodes standardised operating procedures into prompt sequences and assigns assembly-line roles, with agents checking intermediate results. The abstract claims "more coherent solutions than previous chat-based multi-agent systems" and gives no numbers. — [Hong et al., arXiv 2308.00352](https://arxiv.org/abs/2308.00352)
- ChatDev (arXiv Jul 2023, ACL 2024): a "chat chain" fixes what role pairs discuss through design, coding and testing phases, and "communicative dehallucination" governs how. The abstract reports no quantitative results. — [Qian et al., arXiv 2307.07924](https://arxiv.org/abs/2307.07924)
- CAMEL (arXiv Mar 2023, NeurIPS 2023): two-agent role-playing guided by inception prompting, presented mainly as a way to generate conversational data and study agent societies; no measured task results in the abstract. — [Li et al., arXiv 2303.17760](https://arxiv.org/abs/2303.17760)
- AutoGen (arXiv Aug 2023): customisable "conversable" agents whose interaction patterns are programmed in natural language or code; effectiveness is asserted across maths, coding, question answering and other example applications without figures in the abstract. — [Wu et al., arXiv 2308.08155](https://arxiv.org/abs/2308.08155)

Dissent
- Cognition, "Don't Build Multi-Agents" (12 Jun 2025): two principles, share full context (traces, not just messages) and "actions carry implicit decisions, and conflicting decisions carry bad results". Recommends a single-threaded linear agent, plus a dedicated history-compression model for long tasks. Contains no measurements; the author says the theories "are likely not perfect". It notes that Claude Code subagents (as of June 2025) never run in parallel with the main agent and are used to answer well-defined questions, keeping investigation out of the main context. — [Cognition, Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)

### Inferences
- The Anthropic (+90.2% on research) and Cognition (do not build multi-agents) positions are not really in conflict: both say parallel writers with divided context fail, and both accept isolated read-only subagents. The Google scaling study gives the measured version of the same split (large gains on parallel analysis, losses on sequential planning and coding).
- Anthropic's own finding that tokens explain 80% of variance means a large share of any multi-agent gain is "more compute spent in parallel", not architecture. This matters for cost-benefit: the right comparison is a single agent given the same token budget.
- Fleet's shape (deterministic pipeline with one LLM reviewer) is already what all three vendors call the recommended starting point. The evidence supports adding agents only at steps that are (a) independent across repositories or candidates, (b) read-heavy, and (c) currently limited by context size or tool confusion.
- SWE-bench Verified and Terminal-Bench results (-2% to -19%) are the closest published proxies for Fleet's domain and argue against multi-agent authoring of a single task.

### Gaps
- For MetaGPT, ChatDev, CAMEL and AutoGen I read only the arXiv abstracts, none of which states a benchmark figure. The papers' own tables (for example MetaGPT's code-generation scores) were not read, so I have no verified performance numbers for them; the only verified measurement touching them here is the MAST failure-rate range (41-86.7%) above.
- Web search was largely unavailable (one of three searches succeeded), so coverage of NeurIPS/ICLR/ICML 2026 single-versus-multi-agent papers is limited to what I could reach by known URL; there may be relevant 2026 results I did not see.
- The OpenAI guide's publication date is not printed in the PDF (I believe April 2025, unverified). I did not review newer OpenAI material (Agents SDK docs, AgentKit) or Google's ADK documentation, so vendor guidance later than January 2026 may exist that I have not seen.
- Magentic-One's exact GAIA, AssistantBench and WebArena scores were not extractable (chart only).
- Anthropic's 90.2% figure is an internal eval with an LLM judge; no independent replication was found.

## 2. Failure studies: MAST, follow-ups and rebuttals, and proposed fixes

### Takeaway
MAST (2025) finds that multi-agent failures are mostly organisational (specification, coordination, verification) rather than raw model weakness, and that prompt-level fixes help by single to low double digits while leaving failure rates high. The 2026 follow-ups sharpen two points: keep termination and verification outside the model, and many published multi-agent "wins" disappear when compute is held equal.

### Cited Findings
- MAST: 14 failure modes in 3 categories, built from 150 traces and applied to 1,600+ annotated traces (1,642 in v3) across 7 frameworks; human inter-annotator kappa 0.88; arXiv v1 17 Mar 2025, v3 26 Oct 2025; NeurIPS 2025 Datasets and Benchmarks track. — [Cemri et al., arXiv 2503.13657](https://arxiv.org/abs/2503.13657); [NeurIPS 2025 poster](https://neurips.cc/virtual/2025/poster/121528)
- Failure-mode shares (v3): step repetition 15.7%; reasoning-action mismatch 13.2%; unaware of termination conditions 12.4%; disobey task specification 11.8%; incorrect verification 9.1%; no or incomplete verification 8.2%; task derailment 7.4%; fail to ask for clarification 6.8%; premature termination 6.2%; loss of conversation history 2.8%; conversation reset 2.2%; ignored other agent's input 1.9%; disobey role specification 1.5%; information withholding 0.85%. Summed by category this is roughly 44% system design, 32% inter-agent misalignment, 24% task verification (sum computed from the per-mode figures, not stated by the paper in the portion read). — [Cemri et al., arXiv 2503.13657v3](https://arxiv.org/html/2503.13657v3)
- Interventions measured on ChatDev with the same model (GPT-4o): improved role specifications and a topology change giving one agent the final say raised task success by +9.4%; adding a high-level task-objective verification step raised success on ProgramDev by +15.6%, the largest gain reported. The authors conclude tactical fixes are inconsistent and call for structural ones: multi-level verification (not just "does it compile"), better communication protocols, uncertainty quantification, and memory/state management. — [Cemri et al., arXiv 2503.13657v3](https://arxiv.org/html/2503.13657v3)
- MAST's LLM-as-judge annotator (o1, few-shot) reaches 0.94 accuracy and kappa 0.77 against human experts; zero-shot kappa is 0.58. — [Cemri et al., arXiv 2503.13657v3](https://arxiv.org/html/2503.13657v3)
- IBM Research and UC Berkeley applied MAST to 310 ITBench SRE traces (18 Feb 2026). Mean recall: Gemini-3-Flash 75.5%, Kimi-K2 28.6%, GPT-OSS-120B 12.4%. Failure modes per failed trace: 2.6, 4.7, 5.3. — [IBM Research on Hugging Face, ITBench and MAST](https://huggingface.co/blog/ibm-research/itbenchandmast)
- Same study: step repetition and disobeying task specification are often benign (step repetition appears in over 90% of successful Kimi-K2 runs). Modes strongly tied to failure are unaware-of-termination, premature termination, loss of history, task derailment and failure to ask for clarification. For the strongest model the dominant residual failure is incorrect verification (52% more frequent in failed than successful Gemini-3-Flash traces). — [IBM Research on Hugging Face](https://huggingface.co/blog/ibm-research/itbenchandmast)
- Same study, recommendations: externalise verification (require tool-based evidence such as a cleared alert before the agent may exit); keep termination and loop control outside the model; add loop detectors; use a deterministic state machine for weaker models. It cites prior work in which prompt engineering gave up to about 15.6% improvement while architectural changes (summariser agent, state machine) gave up to 53%. — [IBM Research on Hugging Face](https://huggingface.co/blog/ibm-research/itbenchandmast)
- Automated failure attribution is not yet reliable. On the Who&When dataset (failure logs from 127 multi-agent systems, annotated with responsible agent and decisive error step; Apr-Jun 2025), the best of three methods identifies the responsible agent 53.5% of the time and the decisive step 14.2% of the time; some methods are below random, and reasoning models (o1, DeepSeek R1) are judged not practically usable for the task. — [Zhang et al., arXiv 2505.00212](https://arxiv.org/abs/2505.00212)
- Anthropic's long-running coding harness post (26 Nov 2025) lists single-agent failure modes that mirror MAST's: declaring victory too early, marking features done without end-to-end testing, and leaving undocumented state. Its fixes are structural: a JSON feature list where the agent may change only a `passes` field, one feature per session, a progress file plus git commits, and testing as a user would through browser automation. — [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Rebuttal-style evidence on compute parity: Tran and Kiela (Apr 2026) find single-agent systems "consistently match or outperform" multi-agent systems on multi-hop reasoning when reasoning tokens are held constant, across Qwen3, DeepSeek-R1-Distill-Llama and Gemini 2.5. They argue from the data processing inequality, report that API budget-control artifacts and benchmark artifacts inflate apparent multi-agent gains, and state that multi-agent becomes competitive when a single agent's effective context utilisation is degraded or when more total compute is spent. — [Tran and Kiela, arXiv 2604.02460](https://arxiv.org/abs/2604.02460)
- Error amplification by topology (Google, 2025-2026): independent agents 17.2x, decentralised 7.8x, hybrid 5.1x, centralised 4.4x, single agent 1.0x. Conflict inside the same paper: the main effect of error amplification was not statistically significant after controlling for other metrics (p = 0.658). — [Kim et al., arXiv 2512.08296](https://arxiv.org/html/2512.08296)
- Anthropic names an "early victory problem" for verifier subagents: the verifier runs one or two tests, sees them pass and declares success. Mitigations: concrete criteria (run the complete suite), multiple scenarios and edge cases, and negative tests that should fail. — [Anthropic/Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)

### Inferences
- The failure modes that matter most (termination, verification, derailment) are the ones a deterministic harness can own. A pipeline where code decides "done" and containers decide "valid" removes the three modes that the IBM study ties most strongly to failed runs.
- As models improve, the residual failure shifts from coordination to verification: the best model in the IBM study fails mainly by verifying wrongly. This supports keeping Fleet's acceptance in measured container runs and treating any LLM reviewer as advisory.
- MAST's headline failure rates come largely from 2024-era frameworks on GPT-4o-class models, so they overstate failure rates for current models, but the 2026 ITBench application shows the taxonomy still discriminates between success and failure.
- The IBM article classifies incorrect verification and reasoning-action mismatch as both recoverable and fatal in different sections; treat its fatal/benign split as indicative, not settled.

### Gaps
- No dedicated 2026 peer-reviewed rebuttal of MAST was found; the search returned the original paper and the IBM application only. I did not check whether 2026 work has improved on the Who&When attribution accuracies.
- A University of Illinois study reporting that multi-agent systems consume 4-220x more tokens than single agents appeared only in a secondary search summary; I did not open the primary paper, so the figure is unverified.
- Tran and Kiela's benchmark names (reported by secondary sources as FRAMES and MuSiQue) and architecture list were not confirmed from the paper itself.
- MAST per-framework failure rates are in a figure that was not readable.

## 3. Evidence for specific patterns

### Takeaway
The patterns with the best evidence are those that keep one decision-maker and use other model calls as bounded, isolated tools: orchestrator-workers for parallel read-heavy work, sub-agents for context isolation, map-reduce fan-out over independent items, and evaluator loops where the evaluator is grounded in execution. Debate and heterogeneous-model mixing have weak or negative evidence; role-based pipelines (planner, coder, tester, reviewer) are specifically warned against.

### Cited Findings

Orchestrator-workers / centralised supervisor
- Best measured case: +90.2% over single agent on Anthropic's internal research eval (2025) and +80.8% on Finance-Agent in the Google study (2025-2026). Worst measured cases for the same topology: -50.3% on PlanCraft, -19.2% on Terminal-Bench, -3.1% on SWE-bench Verified. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system); [Kim et al., arXiv 2512.08296](https://arxiv.org/html/2512.08296)
- Centralised coordination contains errors best among multi-agent topologies (4.4x amplification versus 17.2x for independent agents) but adds 285% overhead. — [Kim et al., arXiv 2512.08296](https://arxiv.org/html/2512.08296)
- Known weakness: the supervisor paraphrases worker output ("translation" loss); letting workers' output pass through verbatim fixes much of it. — [LangChain, Benchmarking Multi-Agent Architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)
- Anthropic's lead agent runs subagents synchronously, which blocks on the slowest subagent and prevents mid-flight steering; asynchronous execution is described as adding coordination, state-consistency and error-propagation problems. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

Hierarchical planner with ledgers
- Magentic-One's two-ledger orchestrator (plan ledger plus progress ledger, re-plan on stall count > 2) is competitive on GAIA, AssistantBench and WebArena (Nov 2024), but it is also one of the seven systems in MAST's 41-86.7% failure-rate range. — [Microsoft Research, Magentic-One](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/); [Cemri et al., arXiv 2503.13657v3](https://arxiv.org/html/2503.13657v3)
- Hybrid (hierarchical plus peer) topologies carry the highest overhead measured, 515%, and 6.2x the turns of a single agent. — [Kim et al., arXiv 2512.08296](https://arxiv.org/html/2512.08296)

Evaluator-optimizer / generator-critic
- Recommended only where evaluation criteria are clear and iteration demonstrably helps. — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Adding a high-level objective verification step was the single most effective intervention in MAST (+15.6% on ProgramDev), yet verification failures still account for roughly a quarter of all failure modes. — [Cemri et al., arXiv 2503.13657v3](https://arxiv.org/html/2503.13657v3)
- Reflexion (2023): verbal self-critique stored in an episodic buffer, driven by test feedback, reached 91% pass@1 on HumanEval versus 80% for GPT-4 at the time. — [Shinn et al., arXiv 2303.11366](https://arxiv.org/abs/2303.11366)
- With a strong orchestrator model, a separate verification subagent is often unnecessary; it still helps with weaker orchestrators, specialised tools or explicit checkpoints. — [Anthropic/Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)

Debate and model mixing
- "Should we be going MAD?" (Nov 2023, revised Jul 2024): multi-agent debate does not reliably outperform self-consistency and ensembling; debate protocols are more sensitive to hyperparameters and harder to optimise, though tuning agreement levels can make some variants beat non-debate baselines. — [Smit et al., arXiv 2311.17371](https://arxiv.org/abs/2311.17371)
- Self-MoA (Feb 2025): aggregating repeated samples from the single best model beats mixing different models, by 6.6% on AlpacaEval 2.0 and 3.8% on average across MMLU, CRUX and MATH, because mixing lowers average proposal quality. — [Li et al., arXiv 2502.00674](https://arxiv.org/abs/2502.00674)
- Conflict: a secondary summary of Tran and Kiela (2026) says model heterogeneity is the one reliably beneficial ensemble intervention, which runs against Self-MoA. Not confirmed from the paper. — [Tran and Kiela, arXiv 2604.02460](https://arxiv.org/abs/2604.02460); contradicted by [Li et al., arXiv 2502.00674](https://arxiv.org/abs/2502.00674)

Map-reduce fan-out and independent agents
- Independent agents with no cross-checking have the lowest overhead (58%) but the highest error amplification (17.2x) and the worst results on coupled tasks (-70.0% PlanCraft, -14.9% SWE-bench Verified); they were slightly positive on Terminal-Bench (+1.7%). — [Kim et al., arXiv 2512.08296](https://arxiv.org/html/2512.08296)
- Parallelisation (sectioning and voting) is one of Anthropic's five basic workflow patterns, for speed or for multiple perspectives. — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

Agent-as-tool versus handoffs
- OpenAI's manager pattern (agents as tools) is recommended when one agent should keep control of the workflow; handoffs are for triage where the specialist fully takes over. — [OpenAI, A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- On tau-bench retail with distractors (gpt-4o, Jun 2025), handoff-style swarm slightly outperformed supervisor and used fewer tokens. — [LangChain, Benchmarking Multi-Agent Architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)

Context isolation via sub-agents
- Sub-agents may spend tens of thousands of tokens exploring and return a condensed 1,000-2,000 token summary; model recall degrades as context fills ("context rot"). (29 Sep 2025.) — [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Single-agent accuracy collapses and token use climbs once two or more irrelevant tool domains share its context, while multi-agent variants stay flat. — [LangChain, Benchmarking Multi-Agent Architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)
- Even Cognition's anti-multi-agent post accepts read-only question-answering subagents as a way to keep investigation out of the main history. — [Cognition, Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)

Shared-artifact (blackboard-like) coordination
- Anthropic has subagents write outputs to external storage and return lightweight references, to avoid the "game of telephone" and cut token overhead. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- AlphaEvolve and the Darwin Godel Machine coordinate entirely through a shared database or archive of scored candidates, with no agent-to-agent conversation (see section 4). — [AlphaEvolve, arXiv 2506.13131](https://arxiv.org/html/2506.13131v1); [DGM, arXiv 2505.22954](https://arxiv.org/abs/2505.22954)

### Inferences
- A consistent rule emerges: the fewer free-form messages pass between model calls, the better the measured outcome. Artifacts, references and scores travel well; paraphrased summaries do not.
- Fan-out is safe when a deterministic check sits behind each branch. The 17.2x amplification for independent agents is a measurement of unverified fan-out; Fleet's container validation is exactly the missing check, which makes per-repository or per-candidate fan-out the lowest-risk multi-agent addition.
- Evaluator loops work when the evaluator's signal is execution (Reflexion's tests, MAST's objective check) and are weakest when the evaluator is another opinion.
- Debate is not supported by the evidence for a pipeline like Fleet; sampling the best model several times and selecting by measured result is both cheaper and better supported.

### Gaps
- No head-to-head study of classical blackboard architectures for LLM agents was found; the evidence above is indirect (artifact stores and evolutionary archives).
- The original multi-agent debate paper (Du et al., 2023) and "more agents is all you need" style scaling results were not re-read this session.
- LangChain's benchmark publishes charts without exact numbers and uses gpt-4o; it has not, as far as I found, been rerun on 2026 models.

## 4. Search-style and evolutionary agent systems

### Takeaway
These systems replace conversation between agents with a loop of propose, measure, keep: an LLM proposes a change, an automated evaluator scores it, and an archive of scored candidates guides the next proposal. Their efficiency comes from machine-checkable fitness, cheap-first evaluation cascades, a cheap-model-for-volume plus strong-model-for-quality ensemble, and diversity-preserving archives. This is the family that fits Fleet's "measured runs decide" constraint most naturally.

### Cited Findings
- AlphaEvolve (Google DeepMind, Jun 2025) components: a program database combining MAP-Elites with island populations; a prompt sampler that builds prompts from prior programs, their evaluation results and evolved meta-prompts; an ensemble where Gemini 2.0 Flash supplies volume and Gemini 2.0 Pro supplies occasional higher-quality proposals; SEARCH/REPLACE diff edits over marked blocks of a whole codebase; asynchronous parallel evaluation. — [Novikov et al., arXiv 2506.13131](https://arxiv.org/html/2506.13131v1)
- AlphaEvolve evaluation cascade: candidates face increasingly difficult test stages and advance only if they pass each; faulty programs are filtered on small-scale runs first. LLM-graded properties such as simplicity can be added to the score, but the primary signal is the automated evaluator. — [Novikov et al., arXiv 2506.13131](https://arxiv.org/html/2506.13131v1)
- AlphaEvolve versus FunSearch (paper's Table 1): FunSearch evolves a single function of 10-20 lines in Python, needs millions of LLM samples, uses small models with minimal context, and optimises one metric. AlphaEvolve evolves whole files of hundreds of lines in any language, needs only thousands of samples, benefits from state-of-the-art models and rich context and feedback, and handles multiple metrics and evaluations lasting hours. — [Novikov et al., arXiv 2506.13131](https://arxiv.org/html/2506.13131v1)
- AlphaEvolve measured results: a scheduling heuristic recovering on average 0.7% of Google's fleet-wide compute; 23% average kernel speedup and 1% reduction in Gemini training time; 32% FlashAttention kernel speedup; a 48-multiplication algorithm for 4x4 complex matrices (first improvement on Strassen's 49 in that setting); across 50+ maths problems it matched the best known result in about 75% and beat it in about 20%. Ablations find each of evolution, prompt context, meta-prompts, full-file evolution and strong models contributes significantly (numbers only in a figure). — [Novikov et al., arXiv 2506.13131](https://arxiv.org/html/2506.13131v1)
- Darwin Godel Machine (May 2025, revised Mar 2026): a coding agent rewrites its own code; each variant is validated empirically on coding benchmarks instead of by proof; an archive keeps a growing tree of diverse agents as stepping stones. SWE-bench improved from 20.0% to 50.0% and Polyglot from 14.2% to 30.7%; it outperforms baselines without self-improvement or without open-ended exploration. Self-discovered improvements included better edit tools, long-context management and peer review. Run with sandboxing and human oversight. — [Zhang et al., arXiv 2505.22954](https://arxiv.org/abs/2505.22954)
- ADAS (Aug 2024, revised Mar 2025): Meta Agent Search has a meta agent write new agents in code, drawing on an ever-growing archive of earlier discoveries; discovered agents outperform hand-designed ones across coding, science and maths and transfer across domains and models (abstract gives no numbers). — [Hu, Lu, Clune, arXiv 2408.08435](https://arxiv.org/abs/2408.08435)
- AFlow (Oct 2024, revised Apr 2025): Monte Carlo tree search over workflows represented as code, refined by execution feedback; 5.7% average improvement over prior baselines on six benchmarks, and discovered workflows let smaller models beat GPT-4o on specific tasks at 4.55% of its inference cost. — [Zhang et al., arXiv 2410.10762](https://arxiv.org/abs/2410.10762)
- The AI Scientist (Sakana AI and collaborators, Aug 2024): one pipeline generates ideas, writes code, runs experiments, plots results, writes the paper and runs a simulated review, at "less than $15 per paper". The claim that papers exceed a top-conference acceptance threshold is as judged by its own automated reviewer (itself described as near-human at scoring), not by real reviewers. — [Lu et al., arXiv 2408.06292](https://arxiv.org/abs/2408.06292)
- Google's AI co-scientist (Feb 2025, revised Jun 2026): a Gemini-based multi-agent system that generates, critiques and refines hypotheses through a tournament evolution process on an asynchronous task framework; automated evaluation shows hypothesis quality improving as test-time compute scales; some drug-repurposing candidates for acute myeloid leukaemia were validated in vitro. — [Gottweis et al., arXiv 2502.18864](https://arxiv.org/abs/2502.18864)

### Inferences
- What these systems do differently from role-play multi-agent frameworks: agents never talk to each other. The shared state is a set of candidates with measured scores. That removes the inter-agent misalignment category of MAST (about a third of failure modes) by construction.
- The sample-efficiency jump from FunSearch (millions of samples) to AlphaEvolve (thousands) is attributed to richer context and feedback in the prompt, stronger models, and diff-level edits; the lesson for Fleet is that feeding prior measured outcomes back into the proposal prompt is worth more than adding proposers.
- Ideas that transfer directly to a task-generation pipeline: (1) an evaluation cascade ordered cheapest first (static checks, then build, then the full fail-to-pass container run) so expensive containers only run on survivors; (2) cheap model for volume with escalation to a strong model; (3) an archive of accepted and rejected candidates with their measured reasons, sampled into prompts; (4) AFlow or ADAS-style offline search over the pipeline's own prompts and step order, scored by measured acceptance rate and cost.
- The AI co-scientist is the outlier: its ranking signal is an LLM tournament, not a measured run, which is acceptable for hypotheses but would violate Fleet's acceptance rule. Tournament ranking could be borrowed only for prioritising which candidates to measure first.
- DGM-style self-modification optimises the benchmark it is scored on; any Fleet use of it would need the score held out from the agent being modified.

### Gaps
- AI Scientist v2 and independent evaluations of AI Scientist output quality were not read; the v1 success claim rests on its own LLM reviewer, which is the kind of model-opinion gate Fleet rules out.
- FunSearch's own paper (Nature, Dec 2023) was not read directly; its characteristics above come from AlphaEvolve's comparison table.
- The AI co-scientist's named agents (generation, reflection, ranking, evolution, proximity, meta-review) and Elo details are in the full paper, not the abstract I read.
- DGM compute cost and its reported objective-hacking incident were not in the abstract; ADAS numeric gains likewise.
- I did not survey 2026 successors (open-source AlphaEvolve reimplementations, newer self-improving coding agents), so newer results may exist.

## 5. Memory and learning across runs; model routing and cascades

### Takeaway
Cross-run learning works when what is stored is verified and structured (executable skills, itemised playbook entries, test-grounded reflections) and degrades when memory is repeatedly re-summarised. Routing and cascades have strong measured cost savings in question-answering settings, but the evidence for agentic pipelines is thinner, and the vendor advice is to establish a strong-model baseline first and then substitute downward under evals.

### Cited Findings
- Voyager (May 2023): an automatic curriculum, a growing skill library of executable code, and iterative prompting with environment feedback, execution errors and self-verification before a skill is stored. Versus prior methods in Minecraft: 3.3x more unique items, 2.3x longer travel distance, up to 15.3x faster tech-tree milestones. — [Wang et al., arXiv 2305.16291](https://arxiv.org/abs/2305.16291)
- Reflexion (Mar 2023): no weight updates; the agent writes a verbal reflection on task feedback into an episodic memory buffer and conditions later trials on it; 91% pass@1 on HumanEval versus 80% for GPT-4 at the time. — [Shinn et al., arXiv 2303.11366](https://arxiv.org/abs/2303.11366)
- ACE, Agentic Context Engineering (Oct 2025, ICLR 2026): treats context as an evolving playbook maintained by generation, reflection and curation with structured incremental updates. It names two failure modes of memory: brevity bias (summaries drop domain detail) and context collapse (iterative rewriting erodes detail). Reported +10.6% on agent benchmarks and +8.6% on finance benchmarks, matching the top production agent on the AppWorld leaderboard average with a smaller open-source model, using execution feedback without labels. — [Zhang et al., arXiv 2510.04618](https://arxiv.org/abs/2510.04618)
- Anthropic context guidance (Sep 2025): structured note-taking to files outside the context window, compaction that keeps decisions and unresolved issues while dropping redundant tool output, and just-in-time retrieval by reference (paths, queries) instead of preloading. — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- The Darwin Godel Machine and ADAS are a form of cross-run learning where the stored unit is a whole agent design in an archive, selected by measured benchmark score. — [DGM, arXiv 2505.22954](https://arxiv.org/abs/2505.22954); [ADAS, arXiv 2408.08435](https://arxiv.org/abs/2408.08435)
- FrugalGPT (May 2023): three strategies, prompt adaptation, LLM approximation and LLM cascade. A learned cascade matched the best single model (GPT-4) with up to 98% cost reduction, or improved accuracy by 4% at equal cost. — [Chen, Zaharia, Zou, arXiv 2305.05176](https://arxiv.org/abs/2305.05176)
- RouteLLM (Jun 2024, revised Feb 2025): routers trained on human preference data choose between a strong and a weak model per query, cutting cost by over 2x in some cases without quality loss, and they transfer when the model pair is swapped. — [Ong et al., arXiv 2406.18665](https://arxiv.org/abs/2406.18665)
- Tiering inside agent systems: Anthropic's research system uses a stronger lead (Opus 4) with cheaper subagents (Sonnet 4); AlphaEvolve uses Flash for throughput and Pro for quality; AFlow workflows let small models beat GPT-4o at 4.55% of its cost on specific tasks. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system); [AlphaEvolve, arXiv 2506.13131](https://arxiv.org/html/2506.13131v1); [AFlow, arXiv 2410.10762](https://arxiv.org/abs/2410.10762)
- OpenAI's procedure: baseline with the most capable model, set up evals, then replace with smaller models where results stay acceptable. — [OpenAI, A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)

### Inferences
- A cascade needs a trustworthy "good enough" signal to decide when to stop. FrugalGPT and RouteLLM learn that signal; Fleet already has one for free, the container result. Cheap-model-first with escalation on measured failure is therefore unusually well suited to Fleet and does not depend on a learned router.
- The memory designs that hold up share one property: an entry is admitted only after it is verified (Voyager's self-verified skills, Reflexion's test feedback, ACE's execution feedback). For Fleet the analogue is a per-ecosystem playbook of build and test recipes (for example how a given Python project layout is installed and its tests run) written only from runs that passed in containers.
- ACE's finding argues for append-and-curate itemised entries over a periodically rewritten summary document.
- Voyager and Reflexion results are from 2023 on GPT-4-era models; treat the magnitudes as historical and the mechanisms as the durable part.

### Gaps
- No 2026 measurement of cascade savings specifically inside multi-step agent pipelines was found this session; FrugalGPT and RouteLLM are single-query settings from 2023-2024 and their headline numbers ("up to 98%", "over 2x in certain cases") are best cases.
- Experience replay in the reinforcement-learning sense has no direct verified LLM-agent result in these notes; trajectory-reuse methods (for example Agent Workflow Memory, ExpeL) were not checked.
- ACE's latency and rollout-cost reductions are claimed in the abstract without figures.
- I found no study of memory poisoning or stale-playbook risk in pipelines of this kind.

## 6. Verification independence, budgets, checkpointing and durable execution, observability

### Takeaway
The consistent advice is to put verification, termination and budgets in deterministic code outside the model, make verification depend on tool-produced evidence, persist state so a failed run resumes instead of restarting, and trace every step. LLM judges are useful for triage and failure analysis, with measured agreement well short of perfect, which supports keeping them out of the acceptance decision.

### Cited Findings

Verification independence
- Verification should be multi-level, covering low-level correctness and the high-level objective; checks such as "the code compiles" are insufficient. A high-level objective check gave the largest measured gain in MAST (+15.6%). — [Cemri et al., arXiv 2503.13657v3](https://arxiv.org/html/2503.13657v3)
- Externalise verification: require tool-based evidence before an agent may exit. For the strongest model studied, incorrect verification is the mode most associated with failure. — [IBM Research on Hugging Face, ITBench and MAST](https://huggingface.co/blog/ibm-research/itbenchandmast)
- Black-box verification is a good sub-agent boundary because the verifier needs little context; guard against early victory with a full-suite requirement, multiple scenarios and negative tests that must fail. — [Anthropic/Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- LLM-judge reliability, measured: MAST's o1 judge reaches kappa 0.77 against human experts with few-shot examples and 0.58 zero-shot, compared with 0.88 between humans. — [Cemri et al., arXiv 2503.13657v3](https://arxiv.org/html/2503.13657v3)
- Anthropic's own eval used a single LLM judge call with a rubric giving 0.0-1.0 scores and a pass-fail grade, started from about 20 real queries, and was supplemented by human testing that caught source-selection bias the judge missed. For stateful agents, evaluate end state, not each step. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Search systems that work keep the primary fitness signal in an automated evaluator, with staged difficulty, and use LLM grading only as a secondary score. — [AlphaEvolve, arXiv 2506.13131](https://arxiv.org/html/2506.13131v1)

Budgets and termination
- Every run needs an explicit exit condition, including a maximum number of turns; set limits on retries and escalate to a human when they are exceeded. — [OpenAI, A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Keep termination and loop control outside the model and add loop detectors; unaware-of-termination is 12.4% of MAST failure modes and step repetition 15.7%. — [IBM Research on Hugging Face](https://huggingface.co/blog/ibm-research/itbenchandmast); [Cemri et al., arXiv 2503.13657v3](https://arxiv.org/html/2503.13657v3)
- Write effort budgets into delegation (agent count and tool-call ranges per complexity tier); without them the orchestrator over-spawns. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Budget planning figures: multi-agent 3-10x single-agent tokens for equivalent tasks (Anthropic, Jan 2026); about 15x chat (Anthropic, 2025); 58-515% coordination overhead depending on topology (Google, 2025-2026). — [Anthropic/Claude blog](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them); [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system); [Kim et al., arXiv 2512.08296](https://arxiv.org/html/2512.08296)
- Magentic-One bounds wasted work with a stall counter that forces a re-plan after more than 2 stalled steps. — [Microsoft Research, Magentic-One](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)

Checkpointing and durable execution
- Build systems that resume from the point of failure instead of restarting; combine deterministic safeguards (retry logic, regular checkpoints) with letting the agent adapt to tool failures; save the plan to external memory before context truncation; when context nears its limit, summarise completed phases and start fresh subagents. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Use rainbow deployments so that updating the system does not break agents that are mid-run. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Store subagent outputs as external artifacts and pass references, which also makes each step's output a natural checkpoint. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- For work spanning many context windows (26 Nov 2025): an initializer session writes an `init.sh`, a progress log and a first git commit; each later session reads the progress notes and git log, runs a basic end-to-end check before new work, does one unit of work, and ends in a clean committed state. The two "agents" differ only in their first prompt. The post leaves open whether specialised testing or QA agents would beat this single-agent loop. — [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- LangGraph persistence: checkpointers save thread-scoped graph state so a run can resume after interruption or failure; in-memory savers lose state on restart, so production needs a persistent saver (Postgres or SQLite); checkpoints accumulate and need pruning or a retention policy. — [LangGraph docs, persistence](https://docs.langchain.com/oss/python/langgraph/durable-execution)

Observability
- Run full production tracing and monitor decision and interaction patterns; agents are non-deterministic between runs, which makes debugging without traces impractical. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Trace-level failure annotation with a fixed taxonomy (MAST) is usable as an operational metric: failure-mode counts per trace separate strong from weak configurations (2.6 versus 5.3 modes per failed trace). — [IBM Research on Hugging Face](https://huggingface.co/blog/ibm-research/itbenchandmast)
- Sandboxed execution and human approval before irreversible actions are recommended after agents were observed taking unrequested external actions. — [Microsoft Research, Magentic-One](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)

### Inferences
- Fleet's constraint (acceptance by measured container runs only) is the practice the failure literature recommends, not a limitation to work around. A judge that agrees with humans at kappa 0.58-0.77 is adequate for prioritising, labelling failures and deciding what to measure next, and inadequate as an acceptance gate.
- Verification independence has two parts worth separating in the design: the verifier should not share the generator's context (so it cannot inherit its assumptions), and the verdict should come from execution. A reviewer agent that reads the generator's reasoning violates the first even if a container enforces the second.
- For a mostly deterministic pipeline, durable execution reduces to persisting each stage's inputs, outputs and measured results as content-addressed artifacts and making stages idempotent, so LLM calls and container runs are never repeated after a crash. Record model ID, prompt version, token counts and cost per stage so that cost per accepted task is a first-class metric.
- Negative tests transfer directly: a candidate task should be shown to fail before the reference change and pass after it, and known-bad candidates should be injected periodically to confirm the validator still rejects them.

### Gaps
- Durable-execution engines (Temporal, Restate, DBOS) and LangGraph's determinism and durability-mode details were not read; the LangGraph page reached was only the persistence overview. Unverified recollection: these systems require deterministic replay of orchestration code and wrapping side effects (LLM calls, tool calls) in recorded, idempotent steps.
- OpenTelemetry's generative-AI semantic conventions have moved to a separate repository (github.com/open-telemetry/semantic-conventions-genai); the old page no longer carries them and I did not read the new one, so their stability status and agent span definitions as of November 2026 are unconfirmed.
- Automated failure attribution is weak (see section 2: 53.5% agent-level, 14.2% step-level in 2025), so observability currently depends on human-readable traces and fixed taxonomies more than on automatic root-causing.
- I found no published measurement of how much independent (separate-context) verification improves on same-context self-verification, only the qualitative recommendations and the MAST +15.6% result.
- No source gave measured guidance on absolute budget values (tokens or dollars per task); the multiples above are the only quantitative planning inputs.
