## 1. How are the named systems designed (tools, loop, verification step, memory)?

### Takeaway
Nearly every system is a ReAct-style bash loop inside a Docker container plus (a) a pre-pass that reads README/CI/config files to pick a base image, (b) some separate verification step, and (c) a "record" step that turns the successful trajectory into a reproducible artifact (committed image, Dockerfile, or install/test JSON). The systems differ mainly in what surrounds the loop: rollback/snapshots (Repo2Run), a separate verifier plus log-parser generation (RepoLaunch), multi-agent repair loops with a per-repo memory pool (SWE-Factory), cross-repo experience retrieval (EnvPilot), and multi-attempt sampling (SWE-rebench V2, ExecutionAgent, Cursor autoinstall).

### Cited Findings

**RepoLaunch, 2026 multi-language version (Microsoft, arXiv 2603.05026, March 2026)**
- Three stages. Preparation: an agent scans the file tree, reads config/instruction files, selects a base image, starts a container and copies the repo in. Build: a Setup Agent with Bash and WebSearch tools installs dependencies, compiles and looks for regression test commands; a Verify Agent reviews the command history and requires most tests to pass (core and integration tests passing) before the container is committed as an image, otherwise failure is returned to the Setup Agent for retry. Management ("Organize Agent"): produces minimal rebuild commands, minimal test commands, and a Python log parser mapping test names to pass/fail/skip, preferring JSON/XML test output. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- Limits: Setup Agent 60 steps on Linux, 90 on Windows; Verify Agent 20 steps; rebuild/test/parser stages 20 steps each (the appendix says 30 in one place, an inconsistency in the paper); bash command timeout 30 minutes; default model GPT-5-Thinking-Medium. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- A Dockerfile is optional and is reconstructed deterministically from the committed image's layers. No cross-repo experience memory exists; retrieval-based agent memory is listed as future work. No explicit snapshot rollback beyond the Verify-to-Setup retry loop. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- The paper states pre-built base images "do not affect success rate" (they only reduce steps and image size), whereas language-specific instructions injected into the prompt do affect success. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)

**Original RepoLaunch (SWE-bench-Live, Python-only, arXiv 2505.23419, May 2025)**
- An LLM selects relevant files (CI/CD configs, READMEs, install/dev guides), an LLM picks a base image from a candidate list (e.g. `python:3.11`), a ReAct setup agent works in a persistent bash session at `/testbed` (may search the web or the issue tracker; prompt recommends `pip install -e .` and avoiding tox), and a verify agent generates a test command that must print per-test status (e.g. pytest `-rA`), tolerating a few failing tests. The validated container is committed as a Docker image. Temperature 0.0. — [SWE-bench-Live paper](https://arxiv.org/html/2505.23419)
- Historical-commit handling: the pip index is redirected to a proxy that only serves package versions released no later than the base commit's timestamp, to avoid "dependency version drift"; the authors say this "significantly improves setup success rates" but give no number. — [SWE-bench-Live paper](https://arxiv.org/html/2505.23419)
- The earlier Python version used the rule-based pytest-format parser from SWE-bench and had no Management stage. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)

**EnvPilot (arXiv 2609.07357, 9 Sep 2026)**
- "Learn-Retrieve-Act-Evaluate" loop built on the SWE-Agent framework; max 50 turns per task; DeepSeek-V3-0324 at temperature 0. — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)
- Experience memory ("TDM"): entries are `<problem, solution, action>` tuples distilled by DeepSeek-R1 from 781 Multi-SWE-Bench trajectories into 667 entries (85.4% retained), seeded with 3-5 expert few-shot examples; frozen during evaluation. — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)
- Retrieval: an LLM first builds a "codebase profile" (language version, dependency tools, build/test commands) from README, config and CI files, prioritising system-level dependencies in CI steps and Dockerfile `RUN` lines; it then writes hypothetical failure-oriented queries, which are embedded (Qwen3-Embedding-8B), searched in Milvus, and merged by Reciprocal Rank Fusion; top-k = 10. — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)
- Verification: an LLM judge decides "Environment Configuration Success" - assertion failures count as success, a complete test lifecycle is required, compilation required for compiled languages. Judge validated on 460 trajectories: accuracy 98.04%, precision 99.26%, recall 97.45% (2 false positives, 7 false negatives). — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)

**ExecutionAgent (Bouzenia and Pradel, arXiv 2412.10133, Dec 2024; ISSTA 2025)**
- Preparation phase ("meta-prompting"): asks an LLM for 10 language-specific guidelines plus language-independent and container guidelines, and finds and summarises the project's CI/CD scripts and top-5 web search hits. Feedback loop: LLM picks next command, tool executes, an LLM summarises outputs over 200 tokens. — [ExecutionAgent paper](https://arxiv.org/html/2412.10133)
- Tools: `linux_terminal` (74.8% of calls), `write_file` (16.0%), `read_file` (8.2%), `task_done` (1%). Budget: 40 commands per attempt, 3 attempts, 5-minute command timeout; lessons from a failed attempt are carried into the next. — [ExecutionAgent paper](https://arxiv.org/html/2412.10133)

**Repo2Run (ByteDance, arXiv 2502.13681, Feb 2025; NeurIPS 2025)**
- Build phase then record phase. "Dual environment": internal Docker container with five actions (environment monitoring, dependency installation, test running, code editing, bash) and an external controller with three actions (rollback, base image change, result processor that truncates long output keeping head and tail). — [Repo2Run paper](https://arxiv.org/html/2502.13681v4)
- Rollback: a `docker commit` snapshot is taken before each command; on non-zero exit the container reverts to the snapshot; a safe-command list (`cat`, `ls`, `grep`...) is exempt. Base-image change clears all executed commands and restarts; default base `python:3.10`. — [Repo2Run paper](https://arxiv.org/html/2502.13681v4)
- Dockerfile synthesizer: successful commands become `RUN` lines, failed ones are dropped, `export` becomes `ENV`, and unpinned package versions are replaced with the versions actually installed. The agent may not modify or delete original test files. Model: gpt-4o-2024-05-13, temperature 0.2. — [Repo2Run paper](https://arxiv.org/html/2502.13681v4)
- RepoLaunch's authors characterise Repo2Run as limited to Python base images and hard-coded commands (pip install, pytest). — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)

**Installamatic (Milliken et al., 2024) as adapted in EnvBench**
- Two sequential agent stages: a documentation-gathering stage where the agent explores the repo with tools until `finish_search` (returning install-relevant files), then a build stage that summarises requirements (`submit_summary`) and generates the setup output. The original has a repair stage; EnvBench removed it and scored only the first generated script, with shell script output instead of a Dockerfile. — [EnvBench paper](https://arxiv.org/html/2503.14443v1)

**EnvBench (JetBrains Research, arXiv 2503.14443, March 2025)**
- A benchmark, not an agent: 994 repositories (329 Python, 665 JVM). Repos with Docker config files were deliberately removed, and repos a deterministic script could already configure (62 Python = 15.9%, 309 JVM = 31.6%) were removed, so the set is "hard by construction". — [EnvBench paper](https://arxiv.org/html/2503.14443v1)
- Its "Bash Agent" baseline is a simplified ExecutionAgent: one tool (`execute_bash_command`), max 30 iterations, 360 s command timeout, output capped at 5,000 characters; final script contains only commands that exited zero. — [EnvBench paper](https://arxiv.org/html/2503.14443v1)

**SetupBench (Microsoft, arXiv 2507.09063, July 2025)**
- Benchmark of 93 tasks starting from a bare Linux sandbox, spanning seven language ecosystems, five database engines and multi-service orchestration; each task has a natural-language statement and a deterministic success command. Evaluated on OpenHands. — [SetupBench abstract](https://arxiv.org/abs/2507.09063v1)

**SWE-rebench V2 setup stage (Nebius, arXiv 2602.23866, Feb 2026; ICML 2026)**
- Setup agent: mini-SWE-agent v1.14.4 driven by Qwen3-Coder-480B-A35B-Instruct; inspects the repo, attempts installs, revises after build/test errors. Output is an `install_config.json` with an `install` command list and a `test_cmd` (tests verbose, no colour). Success criterion: the full test suite runs without infrastructure or dependency failures. — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- Base Dockerfiles are generated per language from a template; large ecosystems get several base images per major toolchain version (e.g. JDK 11/17/21). Log parsers are LLM-generated from a successful test log per repo and regenerated for up to 5 iterations if parsing fails; most ecosystems need 1-2 parsers per repo, C/C++ more (CTest, GoogleTest, Catch2). — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- Language-specific parts are limited to reusable templates (base images, runners, parsers); the workflow is otherwise identical across 20 languages. — [SWE-rebench V2 paper](https://arxiv.org/pdf/2602.23866)

**SWE-Factory / SWE-Builder (arXiv 2506.10954, June 2025)**
- Four agents. Repository Explorer (tools `browse_file`, `browse_directory`, `search_file_by_keyword`; max 10 retrieval rounds); Environment Manager (writes/updates the Dockerfile, keeps generation history, falls back to the previous Dockerfile on failure); Test Manager (writes the evaluation script and appends exit-code capture); Test Analyst (builds, applies gold patch, runs, diagnoses, routes targeted feedback to the responsible agent). Max 5 iterations; averages 3.21-3.57 iterations used. — [SWE-Factory paper](https://arxiv.org/html/2506.10954v2)
- Memory pool: every validated Dockerfile + test script is archived; a new issue retrieves a setup from the same repository, preferring a nearby software version, as its starting point. — [SWE-Factory paper](https://arxiv.org/html/2506.10954v2)

**Repo2RLEnv bootstrap (Hugging Face; package v0.9.6 dated 10 Nov 2026)**
- (From search-result snippets of the project docs, not a full read.) Bootstrap = creating a Docker image where a given repository builds cleanly and its test suite runs; an LLM agent iterates shell commands in a fresh container "until the repo builds and the test suite collects". It is normally triggered automatically: `repo2rlenv generate --pipeline pr_runtime` does a cache lookup and runs bootstrap on a miss; `repo2rlenv bootstrap` can be run standalone to pre-warm or debug. — [repo2rlenv on PyPI (0.4.0)](https://pypi.org/project/repo2rlenv/0.4.0/)
- `pr_runtime` scoring uses the repository's own tests: "failing ones must pass, passing ones must stay green"; native runtime pipelines use local Docker; tasks pass controls when "oracle scores 1, no-op scores 0". — [Repo2RLEnv README](https://github.com/huggingface/Repo2RLEnv)
- From v0.9.0 (15 Sep 2026) a separate "Tasksmith" agent (LangGraph orchestrating Pi or OpenCode agents, running on Daytona or Modal) bootstraps the repo environment on a remote worker, designs a task and private verifier from a merged PR, and "reviews and fixes its own output until its checks pass", recording evidence and cost per stage. — [repo2rlenv on PyPI](https://pypi.org/project/repo2rlenv/)

**Adjacent systems found**
- Cursor "autoinstall" (blog, 6 May 2026): two-stage. Stage 1 (goal setting) proposes 10 commands plus a description of the expected output if setup is correct; Stage 2, a separate agent, is given three of those commands and must make them work. Verification checks that all three run and output matches the Stage 1 description; Stage 2 restarts on failure; after five failed repetitions the environment is discarded. The agent mocks missing components (MinIO for S3, fake DB tables, placeholder images). — [Cursor blog](https://cursor.com/blog/bootstrapping-composer-with-autoinstall)
- Other 2025-2026 work surfaced but not read: Multi-Docker-Eval benchmark (arXiv 2512.06915, read), EvoConfig (arXiv 2601.16489), RAT/RunAnyThing (arXiv 2604.23190), EnConda-Bench (arXiv 2510.25694), PIPer (arXiv 2509.25455), BootstrapAgent (arXiv 2605.15815). — [search listing via EnvPilot query](https://arxiv.org/pdf/2609.07357)

### Inferences
- The stable architectural consensus is: profile repo from static files -> choose base image -> interactive bash loop -> independent verification -> freeze into reproducible artifact -> generate per-test log parser. Fleet's single reviewer proposing a recipe in one shot corresponds to the "zero-shot LLM"/"non-interactive pipeline" baselines, which are consistently the weakest configuration in every paper that measured them (see section 2).
- Three distinct "freeze" strategies exist: commit the container (RepoLaunch), synthesise a Dockerfile from only-successful commands with pinned versions (Repo2Run), or emit a small JSON recipe of install commands + test command replayed on a templated base image (SWE-rebench V2). The JSON-recipe form is closest to Fleet's base-image/install/test triple.

### Gaps
- Repo2RLEnv bootstrap agent's tools, step limits, cache keys and verification details: the docs page (huggingface.github.io/Repo2RLEnv/pipelines/pr_runtime/) could not be fetched (rate limit). Only snippet-level information is available.
- BootstrapAgent (arXiv 2605.15815, "Distilling Repository Setup into Reusable Agent Knowledge") is directly relevant to experience reuse but its PDF could not be parsed; no findings recorded.
- SetupBench agent-side details beyond the abstract were not read.
- Original Installamatic paper was not read directly; description is via EnvBench's adaptation.

## 2. What success rates, costs and time per repository are reported, and how do they change with retries, stronger models, or multiple attempts?

### Takeaway
Reported success ranges from under 10% (zero-shot on EnvBench Python, 2025) to 70-97% build success for 2026 agents with frontier models, but numbers are not comparable across papers because success definitions differ (tests merely executable vs. fail-to-pass validated). LLM cost is small - roughly $0.03-$0.30 per repo with cheap models and $0.7-$2.7 with GPT-5-class reasoning models - while wall-clock is 20-75 minutes; multiple independent attempts and stronger models each produce large gains (pass@1 to pass@10 roughly doubles; a model swap moved RepoLaunch build rate from 77.8% to 96.7%).

### Cited Findings

**Success rates**
- RepoLaunch (2026), task-creation funnel, stage-wise retention (not end-to-end): Build / Management / Validation-retained - Python (old version) 76.2% (528/693) / n.a. / 18.9%; JS/TS 89.1 / 92.2 / 54.0; C/C++ 79.1 / 85.2 / 25.0; C# 92.0 / 95.2 / 35.5; Java 78.0 / 94.0 / 43.0; Go 72.3 / 94.8 / 67.1; Rust 72.1 / 81.0 / 50.0; Windows 70.5 / 80.0 / 35.7. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- RepoLaunch vs others on 119 SWE-bench-style instances: RepoLaunch build 78.2% (93/119), then manage+validate 80.7% (75/93); SWE-agent build 62.2% (74/119), manage+validate 51.4%; Repo2Run on the Python subset 60.6% (20/33) vs RepoLaunch 78.8% (26/33). — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- RepoLaunch ablation on 90 repos (15 per language): baseline GPT-5 build 77.8%, management 85.6%; unlimited time/RAM/CPU 84.4% / 90.0%; adding a string-replace file-edit tool raised build to 88.9% (not used for benchmark building because bugs must be preserved); swapping the model to Claude Opus 4.5 (printed as "Claude-Oups-4.5" in the extraction) gave build 96.7%, management 100%. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- RepoLaunch on other platforms (GPT-5-Thinking-Medium): Android 23/25 build, 23/23 management; embedded Linux 22/25 build, 22/22 management. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- EnvPilot on its AES-Bench (112 instances, 9 languages), DeepSeek-V3-0324, LLM-judged success: EnvPilot 75.00%, SWE-Agent 62.50%, RepoLaunch 55.36%, ExecutionAgent 43.75%, Repo2Run 66.67% (Python only, 12 instances). With GPT-4o-mini: EnvPilot 46.43%, RepoLaunch 40.18%, SWE-Agent 24.11%, ExecutionAgent 23.21%, Bash-Agent 20.54%, Repo2Run 25.00%. On ExecutionAgent's 50-project benchmark (DeepSeek-V3 / GPT-4o-mini): EnvPilot 72 / 46, SWE-Agent 56 / 28, RepoLaunch 50 / 30, ExecutionAgent 36 / 18; Installamatic 0%. — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)
- EnvPilot run-to-run variance at temperature 0 over 3 trials: 74.11 +/- 4.09 (range 69.64-77.68) with memory; 62.20 +/- 2.25 without. — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)
- ExecutionAgent (GPT-4o era, Dec 2024), 50 projects in 14 languages: built 41/50, test suite executed 33/50, within 10% of ground-truth test counts 29/50. Baselines: LLM-written scripts 29 built / 5 executed; AutoGPT 9 / 4; Flapy 0/10 executed on Python. — [ExecutionAgent paper](https://arxiv.org/html/2412.10133)
- Repo2Run (GPT-4o, Feb 2025), 420 Python repos created in 2024 with >100 stars: 86.0% (361) "environment building success" (tests executable by pytest regardless of outcome), 100% Dockerfile build; LLM-generator baseline 22.1%, SWE-agent 9.0%, pipreqs 6.0%. No repeated runs or error bars. — [Repo2Run paper](https://arxiv.org/html/2502.13681v4)
- EnvBench (March 2025; GPT-4o / GPT-4o-mini), pass@1: Bash Agent 6.69% (22/329) Python and 29.47% (196/665) JVM with GPT-4o; zero-shot 5.47% Python / 8.57% JVM; Installamatic 4.86% Python / 1.35% JVM. On a 30-repo Python sample expert-written scripts reached 66.7% vs 10.0% for the best baseline. — [EnvBench paper](https://arxiv.org/html/2503.14443v1)
- SetupBench (July 2025, OpenHands): repository-setup tasks 38.9-57.4% success, local database configuration 20.0-53.3% (ranges across models). — [SetupBench abstract](https://arxiv.org/abs/2507.09063v1)
- SWE-rebench V2: "only about 20% of repos succeed with one setup attempt" in the production pipeline (1 setup run per repo). Funnel: 21,692 repos / 583,809 PRs after repo filtering -> 4,006 repos / 41,349 tasks with a successful fail-to-pass -> 3,617 repos / 32,079 tasks after issue-clarity filtering. — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- SWE-Factory (671 issues, 4 languages; June 2025): GPT-4.1-mini valid (fail-to-pass) rate 40.1% (269), build "success" rate 57.2% (384); Gemini-2.5-flash 33.5% / 49.8%; DeepSeek-v3-0324 34.6% / 50.8%. Per-language valid rate with GPT-4.1-mini: Python 39.4%, Java 28.5%, TypeScript 54.0%, JavaScript 38.7%. — [SWE-Factory paper](https://arxiv.org/html/2506.10954v2)
- Multi-Docker-Eval (Dec 2025; 334 issues, 40 repos, 9 languages, PRs after 31 Jul 2025), fail-to-pass rate: SWE-Builder averaged 30.58% (+/-6.54) across models vs RepoLaunch 8.85% (+/-3.11); best single result 37.72% (SWE-Builder + DeepSeek-v3.1). "Commit" (self-declared success) rates were 45.92% and 22.35% respectively. — [Multi-Docker-Eval paper](https://arxiv.org/html/2512.06915v3)

**Cost and time**
- RepoLaunch (GPT-5-Thinking-Medium), per instance over all three stages: C/C++ $2.684 (3,438.8k input tokens, 13,144 output), C# $1.783, JS/TS $1.730, Rust $1.483, Go $1.388, Java $1.234; Python (old version without Management stage) $0.663; text average "about $1.7". Single-command repos cost "around $0.15", yet about one-third of those still hit errors. Wall-clock per repo not reported. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- EnvPilot comparison, per repo with DeepSeek-V3: EnvPilot $0.063 (28 API calls, 220k tokens); SWE-Agent $0.058; RepoLaunch $0.071 (34 calls, 250k); ExecutionAgent $0.130 (420k); Repo2Run $0.281 (1,000k tokens). — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)
- ExecutionAgent: average $0.16 per project (about $0.10 for successes, $0.34 for failures because failures exhaust the budget); average 74 minutes per project. — [ExecutionAgent paper](https://arxiv.org/html/2412.10133)
- Repo2Run: 29.03 minutes average for successful builds; 30.7% of successes under 10 minutes; manual setup in the authors' sample averaged 21.33 minutes; about 18 dependency-install actions and 3.5 test runs per successful build; base image changed in 13.3% of successes. Dollar cost not reported. — [Repo2Run paper](https://arxiv.org/html/2502.13681v4)
- EnvBench average cost per repo: zero-shot GPT-4o $0.03-0.042, Bash Agent GPT-4o $0.15 (Python) / $0.20 (JVM), GPT-4o-mini $0.01-0.02; agents use about 5-10x the tokens of zero-shot. — [EnvBench paper](https://arxiv.org/html/2503.14443v1)
- SWE-Factory: $0.045 per instance and 22.4 min (GPT-4.1-mini); $0.024 and 27.0 min (Gemini-2.5-flash); $0.043 and 22.5 min (DeepSeek-v3). Java is the most expensive language ($0.042-0.078). — [SWE-Factory paper](https://arxiv.org/html/2506.10954v2)
- Multi-Docker-Eval per-run token averages: SWE-Builder 165.95k input / 42.15k output; RepoLaunch 504.05k input / 10.03k output; average image size about 1.0-1.4 GB. Dollar cost not reported. — [Multi-Docker-Eval paper](https://arxiv.org/html/2512.06915v3)

**Effect of retries, attempts and model strength**
- SWE-rebench V2 ablation (103 tasks, 10 languages, 10 runs each), pass@1 -> pass@10: non-interactive fixed 3-step pipeline 12.1 -> 15.7; mini-SWE-agent + Qwen3-30B (32k context) 17.4 -> 46.1; + DeepSeek-V3.2 20.3 -> 59.8; + Qwen3-480B (32k) 25.8 -> 58.8; + Qwen3-480B (128k) 27.1 -> 62.7. Retries are framed as a cost-yield trade-off configurable per language or repo. — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- A secondary review of SWE-rebench V2 states interactive agents beat the non-interactive pipeline even when the latter uses a stronger model. — [SWE-rebench V2 paper](https://arxiv.org/pdf/2602.23866)
- ExecutionAgent ablations (tests executed out of 50 / cost): full 33 / $0.16; no feedback loop 5 / $0.02; no preparation phase 8 / $0.19; no guidelines 15 / $0.15; no CI/web retrieval 24 / $0.18. Success-by-attempt curve across the 3 outer attempts is not reported. — [ExecutionAgent paper](https://arxiv.org/html/2412.10133)
- Repo2Run ablations (EBSR): without dual environment 41.7%; without rollback 83.6% (vs 86.0% full) and 96.9% buildable Dockerfiles (vs 100%); without Dockerfile synthesizer 13.8%. — [Repo2Run paper](https://arxiv.org/html/2502.13681v4)
- EnvPilot ablation: removing the memory drops success from 75.00% to 62.50%; retrieval size k=0/5/10/15/20 gives 64.29 / 68.75 / 75.00 / 74.11 / 71.43 (too many retrieved experiences hurts). For C/C++ the no-memory variant (68.00%) beat every memory variant. — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)
- Multi-Docker-Eval: model size and reasoning length are "not decisive"; open models (DeepSeek-v3.1, Kimi-K2) match or beat Claude Sonnet 4 and GPT-5-mini; framework choice (SWE-Builder vs RepoLaunch) changes fail-to-pass by roughly 2.5-3.5x, far more than model choice. Thinking models produced better scripts but more Docker failures. — [Multi-Docker-Eval paper](https://arxiv.org/html/2512.06915v3)
- Coding-agent harness matters less than the model in RepoLaunch's downstream benchmark (SWE-agent 29.6%, Claude Code 29.2%, OpenHands 27.9% averaged over models; models range 20.6%-35.8%). Note this is task-solving on the produced benchmark, not environment setup. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)

### Inferences
- The cheapest reliable lever in the literature is multiple independent attempts with an interactive agent: pass@10 is 2-2.7x pass@1 for interactive agents but barely moves (12.1 -> 15.7) for a non-interactive pipeline. For Fleet this argues for "N cheap interactive attempts, keep the first that verifies" over one expensive single-shot reviewer.
- LLM token spend is not the scaling bottleneck: with DeepSeek/4o-mini-class models it is $0.03-$0.30 per repo, i.e. tens to low hundreds of dollars per thousand repos; with GPT-5-class reasoning models $0.7-$2.7 per repo ($700-$2,700 per thousand). Wall-clock (20-75 min/repo) and container compute/RAM (RepoLaunch used 3 machines with 96 cores and 1 TB RAM each for 30 days; timeouts/OOM are a leading failure cause) are the real costs.
- Failures cost more than successes (ExecutionAgent: $0.34 vs $0.10) because they exhaust the budget; an early-abort classifier or cheap deterministic pre-filter saves disproportionately.
- RepoLaunch's reported disparity between its own paper (78% build) and Multi-Docker-Eval (8.85% fail-to-pass, older RepoLaunch version, weaker/cheaper models, stricter metric) shows how much the success definition and model choice dominate headline numbers; any single cited percentage needs its metric stated.

### Gaps
- No source gives a clean cost-vs-yield curve in dollars for retries (SWE-rebench V2 gives pass@k without cost; ExecutionAgent gives no per-attempt breakdown).
- RepoLaunch wall-clock per repo and Repo2Run dollar cost are not reported.
- No paper found reports results for late-2026 frontier models specifically on historical (multi-year-old) commits; all benchmarks sample recent repos/PRs.
- The 96.7% Claude Opus 4.5 figure in RepoLaunch has no stated sample size in the extraction (presumably the same 90 repos); verify in the PDF.

## 3. What role do deterministic sources (CI workflows, tox/nox, Dockerfiles, lockfiles, README) play versus agent exploration, and which is more reliable?

### Takeaway
Deterministic sources are used almost everywhere as LLM context (a "profile" or "preparation" pre-pass), not as executed recipes; the evidence says purely deterministic scripts and non-interactive pipelines top out low (roughly 16-32% of repos, or 12-16% pass@k), while feeding CI/config information into an interactive loop measurably helps. No paper found directly measures "execute the CI workflow verbatim" against agent exploration.

### Cited Findings
- EnvBench's deterministic baseline script (standard commands per dependency manager) configured 15.9% of Python repos (62) and 31.6% of JVM repos (309) before filtering; these were then excluded from the benchmark. On the remaining hard set the deterministic script had non-zero exit on 28.57% of Python and 1.35% of JVM repos, vs Bash Agent GPT-4o 5.78% / 17.74% and zero-shot GPT-4o 52.58% / 81.20%. — [EnvBench paper](https://arxiv.org/html/2503.14443v1)
- EnvBench: relative to the deterministic script, LLM baselines produced more missing imports on 13-24% of repositories (average increase at least 200%) and fewer on 31-53% (average decrease about 50-60%) - i.e. agents sometimes make things worse than the default recipe. — [EnvBench paper](https://arxiv.org/html/2503.14443v1)
- Repo2Run's rule-based baseline pipreqs: 6.0% environment success; 63.1% of repos failed during download due to version conflicts, 7.1% at requirements generation. — [Repo2Run paper](https://arxiv.org/html/2502.13681v4)
- SWE-rebench V2: the non-interactive fixed 3-step pipeline reached 12.1% pass@1 / 15.7% pass@10 vs 25.8% / 58.8% for the interactive agent with the same model family. — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- ExecutionAgent: retrieving and summarising CI/CD scripts and web results is part of the preparation phase; removing CI/web retrieval cut executed test suites from 33 to 24 of 50; removing the whole preparation phase cut it to 8. Projects with build-tool config files: 28/38 tested; without: 5/12. — [ExecutionAgent paper](https://arxiv.org/html/2412.10133)
- EnvPilot builds its codebase profile from README, config and CI files, explicitly prioritising system-level dependencies in CI steps and Dockerfile `RUN` commands while ignoring docker build/run commands; there is no separate deterministic parser. — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)
- Original RepoLaunch has an LLM select CI/CD configs, READMEs and install guides as context, and its prompt advises avoiding tox where possible in favour of an editable install. — [SWE-bench-Live paper](https://arxiv.org/html/2505.23419)
- RepoLaunch 2026: single-command repos (a standard install/test invocation suffices) cost around $0.15 but about one-third still encounter errors. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- Multi-Docker-Eval labels 20.06% of its instances "Easy" (buildable with simple commands such as `pip install -r requirements.txt`); even on these, fail-to-pass success was only 39.10% (SWE-Builder) and 21.71% (RepoLaunch). — [Multi-Docker-Eval paper](https://arxiv.org/html/2512.06915v3)
- Zero-shot prompting that includes README, config files and Dockerfile info still failed: 5.47% Python / 8.57% JVM pass@1 on EnvBench; the authors note approaches without explicit error feedback commonly produce erroneous scripts. — [EnvBench paper](https://arxiv.org/html/2503.14443v1)
- Cursor autoinstall's goal-setting stage reads READMEs, Makefiles and language tooling (uv, clippy) to propose target commands, then verifies against them. — [Cursor blog](https://cursor.com/blog/bootstrapping-composer-with-autoinstall)
- EnvBench removed repositories containing Docker config files from its dataset on the premise that they are already (easier to be) configured. — [EnvBench paper](https://arxiv.org/html/2503.14443v1)

### Inferences
- A tiered design is supported by the numbers: a deterministic pass (standard recipe per dependency manager, CI-derived test command) is nearly free and resolves a meaningful minority (roughly 15-30% of recent repos), but must itself be verified because standard recipes fail a third of the time even on "single-command" repos; everything else needs an interactive loop.
- The highest-value use of CI files is as hints for system packages, language version matrix and the exact test invocation, injected into the agent's context (ExecutionAgent's ablation: -27% executed suites without it), not as a script to replay. Tox/nox are explicitly avoided by RepoLaunch because they re-create environments and need network.
- For historical commits, deterministic sources decay: lockfiles pin Python deps but not system libraries or the interpreter; unpinned requirements resolve to present-day versions (see section 6), so "deterministic" recipes are only deterministic with a date-bounded index.

### Gaps
- No controlled study found comparing "parse and execute the repo's own GitHub Actions workflow" against agent exploration, nor one measuring how often repos' own Dockerfiles build at historical commits.
- No evidence found specifically on lockfile-driven setup (uv.lock/poetry.lock) success rates versus requirements.txt.

## 4. How do systems reuse experience across repositories or commits?

### Takeaway
Four reuse mechanisms are documented: per-repo recipe reuse across commits (SWE-rebench V2: one setup per repo; SWE-Factory: memory pool keyed by repo and nearest version), cross-repo distilled experience retrieval (EnvPilot: +12.5 points), container snapshots/rollback within a run (Repo2Run, RepoLaunch image commits), and carrying lessons across attempts (ExecutionAgent). Per-repo recipe reuse is the mechanism used at the largest scale; quantitative ablations exist only for EnvPilot's memory and Repo2Run's rollback.

### Cited Findings
- SWE-rebench V2 infers setup once per repository, on the snapshot of the latest mined task, and reuses it for all that repo's tasks (32,079 issue tasks from 3,617 repos plus 120,000+ PR-derived tasks). The paper acknowledges setup may differ across commits/toolchain versions and lists handling multiple repo states as future headroom. — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- SWE-Factory's memory pool archives each validated Dockerfile and test script and, for a new issue, retrieves one from the same repository preferring a nearby software version as the baseline; the paper provides no ablation isolating the pool. — [SWE-Factory paper](https://arxiv.org/html/2506.10954v2)
- Multi-Docker-Eval attributes SWE-Builder's 2.5-3.5x advantage over RepoLaunch to its repair loop (four agents + memory pool vs single agent with no retry/reuse) but does not isolate the memory pool's effect. — [Multi-Docker-Eval paper](https://arxiv.org/html/2512.06915v3)
- EnvPilot's cross-repo memory (667 `<problem, solution, action>` entries from repos disjoint from the test set): +12.5 points (62.50 -> 75.00) at essentially equal cost ($0.062 vs $0.057 per repo). Partial variants (naive retrieval, unstructured memory, problem+solution only, problem+action only) all scored 66.96%; the paper attributes the gain to the full triple plus profile-conditioned retrieval. Retrieving more than 10 items reduced success. — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)
- ExecutionAgent carries lessons from a failed attempt into the next of up to 3 attempts; language guidelines are generated once per language by meta-prompting; removing guidelines dropped executed suites from 33 to 15. — [ExecutionAgent paper](https://arxiv.org/html/2412.10133)
- Repo2Run snapshots the container with `docker commit` before every non-safe command and rolls back on failure; ablating rollback cost 2.4 points of success (86.0 -> 83.6) and left 3.1% of Dockerfiles unbuildable. — [Repo2Run paper](https://arxiv.org/html/2502.13681v4)
- RepoLaunch commits the verified container as a reusable image and can deterministically reconstruct a Dockerfile from the image layers; it offers pre-built base images per language that reduce steps and image size without changing success rate; experience memory is future work. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- SWE-rebench V2 uses a small set of per-language base images (multiple per major toolchain version, e.g. JDK 11/17/21) shared across repositories. — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- Repo2RLEnv performs a cache lookup before bootstrap and only runs the agent on a miss; bootstrap can be pre-warmed standalone (snippet-level evidence). — [repo2rlenv on PyPI (0.4.0)](https://pypi.org/project/repo2rlenv/0.4.0/)
- BootstrapAgent (arXiv 2605.15815, May 2026) frames setup exploration as distillable, reusable agent knowledge (title/abstract-level only). — [BootstrapAgent paper](https://arxiv.org/pdf/2605.15815)

### Inferences
- For a pipeline mining many commits per repo, the dominant saving is amortisation: solve a repo once, replay the recipe at neighbouring commits, and only re-invoke the agent when replay fails verification. SWE-Factory's "nearest version" retrieval is the closest published analogue to environment "eras" (contiguous commit ranges sharing one recipe); no paper found uses the term or formally segments history into eras.
- SWE-rebench V2's choice to set up at the latest snapshot and reuse backwards is a known weakness for historical commits (the paper flags it); a pipeline targeting old commits should key cached recipes on (repo, dependency-manifest hash or date range) rather than repo alone.
- Cross-repo memory helps on average but can hurt on idiosyncratic builds (C/C++ in EnvPilot) and adds run-to-run variance (+/-4.09 vs +/-2.25), so it should be advisory context, capped at about 10 items.
- Image layering as practised: shared language/toolchain base image -> per-repo dependency layer (committed image or synthesised Dockerfile) -> per-commit source checkout. Only the middle layer needs an agent.

### Gaps
- No quantitative data found on how often a recipe from one commit works at another commit of the same repo (replay hit rate vs commit distance), which is the key number for an "era" cache.
- No ablation of SWE-Factory's memory pool exists in its paper or in Multi-Docker-Eval.
- Repo2RLEnv's cache key structure (per repo vs per commit) is unknown (docs not retrievable).

## 5. How do they verify a setup is actually correct rather than merely exiting zero?

### Takeaway
Verification ranges from weak (tests are executable; exit code) to strong (per-test parsed statuses compared with CI ground truth or with a fail-to-pass transition under a gold patch). The evidence is that self-declared or exit-code success substantially overstates true success: commit rates run 1.5-2.5x fail-to-pass rates, 12.7% of failures are silent false passes, and all of SWE-Factory's fail-to-pass false positives were collection errors masquerading as failing tests.

### Cited Findings
- RepoLaunch: Verify Agent requires most tests passing (core/integration passing) before commit; a human check of 100 Verify-passed instances found two incomplete builds. The Organize stage then generates a per-test log parser (test name -> pass/fail/skip), preferring structured JSON/XML reports; "failure to parse test logs" is the largest Management-stage failure category (e.g. C# 63.5%, Java 56.3% of Management failures). — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- Original RepoLaunch requires the test command to print per-test status (pytest `-rA`); benchmark validation requires at least one FAIL_TO_PASS transition and runs tests multiple times, keeping only instances with consistent results across all runs (number of runs unspecified). — [SWE-bench-Live paper](https://arxiv.org/html/2505.23419)
- ExecutionAgent compares counts of passed/failed/skipped tests with manually established ground truth from the projects' CI/CD logs: 17 of 33 executed projects matched exactly; the other 16 deviated by 15.4% on average (7.5% average over all 33); in deviating projects 99.9% of passing tests aligned and differences came mostly from failing tests. — [ExecutionAgent paper](https://arxiv.org/html/2412.10133)
- Repo2Run's formal definition requires all tests to run, but its reported metric counts success when tests can be executed by pytest regardless of pass/fail. RepoLaunch, when re-evaluating Repo2Run, used "more than half of tests pass" as the bar. — [Repo2Run paper](https://arxiv.org/html/2502.13681v4); [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- EnvBench avoids tests entirely: Python success = zero pyright `reportMissingImports` errors and zero exit code; JVM success = `gradle build`/`mvn compile` with zero errors. The authors present this as a lighter proxy than test-suite metrics. — [EnvBench paper](https://arxiv.org/html/2503.14443v1)
- EnvPilot uses an LLM judge over the test log (assertion failures count as success; complete test lifecycle required): 98.04% accuracy vs human labels on 460 trajectories. — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)
- SWE-rebench V2: applies the test patch and runs the full suite, applies the solution patch and runs again, keeps only instances with at least one fail-to-pass test, parsed by repo-specific LLM-generated log parsers; an ensemble of LLM judges (calibrated against human-verified SWE-bench annotations) filters unsound instances afterwards. No repeated-run flakiness check is described. — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- SWE-Factory grades by exit code (script appends `rc=$?` and echoes a sentinel): 100% agreement with manual judgment on 2,085 reports. But exit-code fail-to-pass validation had precision 92% (60 false positives of 778 flagged; recall 100%), and every false positive was an "error2pass" case - tests could not even be collected/imported before the patch (e.g. ImportError for a symbol the gold patch introduces). The authors recommend filtering these. — [SWE-Factory paper](https://arxiv.org/html/2506.10954v2)
- Multi-Docker-Eval: self-declared "commit" rate overstates fail-to-pass success (SWE-Builder 45.92% vs 30.58%; RepoLaunch 22.35% vs 8.85%; Claude Sonnet 4 47.41% vs 35.53%); authors attribute RepoLaunch's gap to weak automated validation. Among SWE-Builder failures: Docker build errors 36.09%, missing/non-executable scripts 18.12%, silent false passes (test passes on unpatched code) 12.70%. — [Multi-Docker-Eval paper](https://arxiv.org/html/2512.06915v3)
- Cursor autoinstall verifies against a pre-registered expectation: Stage 1 writes down the expected output before execution, and Stage 2's result must match it for three sampled commands. — [Cursor blog](https://cursor.com/blog/bootstrapping-composer-with-autoinstall)
- Repo2RLEnv gates tasks on control runs: the oracle (reference solution) must score 1 and a no-op must score 0; bootstrap's stated completion condition is that the repo builds and the test suite collects (snippet-level). — [Repo2RLEnv README](https://github.com/huggingface/Repo2RLEnv); [repo2rlenv on PyPI (0.4.0)](https://pypi.org/project/repo2rlenv/0.4.0/)
- SWE-rebench V2 notes compiled C/C++ builds can reuse stale artifacts unless an explicit rebuild runs after the patch is applied, and Scala output ordering varies so structured XML reports are preferred. — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)

### Inferences
- A defensible verification ladder, in increasing strength: (1) exit code; (2) test collection count > 0 and no collection/import errors; (3) per-test statuses parsed from structured output (JUnit XML / JSON), with a pass-fraction threshold; (4) agreement with an independent reference (CI logs, or a second independent run); (5) behavioural controls - gold patch flips specific tests fail->pass, no-op does not; (6) repeated runs for flake detection. Published pipelines that stop at (1) or at agent self-assessment show 8-40% contamination-type errors.
- Distinguishing "error" (collection/import failure) from "fail" (assertion) at the per-test level is the single most valuable parser feature: it is exactly what separates SWE-Factory's 60 false positives from true fail-to-pass.
- Log parsing is itself a major failure surface (the top Management-stage failure in RepoLaunch); forcing structured reporters (pytest `--junitxml`, `go test -json`, etc.) in the test command reduces dependence on LLM-written parsers.
- An independent verifier that did not perform the setup (RepoLaunch's Verify Agent, Cursor's pre-registered goals, SWE-Factory's Test Analyst) is a recurring pattern; self-verification by the setup agent is what Multi-Docker-Eval shows to be unreliable.

### Gaps
- No source found reports using "collected-test count compared against an expected count" (e.g. from CI logs at that commit) as an automated gate at scale; ExecutionAgent's CI ground truth was manual on 50 projects.
- The number of repeated runs used for flake filtering is unspecified in SWE-bench-Live; SWE-rebench V2 does not describe one.
- Repo2RLEnv's verification details (collected-test counts, reruns) could not be confirmed from its docs.

## 6. What are the documented failure modes?

### Takeaway
The dominant documented failures are resource/timeouts and toolchain/runtime version mismatches, followed by native/system dependencies, test-log parsing, and repo-state problems; compiled languages (C/C++, Rust, Java) are consistently hardest. Dependency drift at historical commits is acknowledged and mitigated by exactly one published mechanism (a date-bounded package index); network-at-test-time is mentioned only in passing, and old-interpreter problems are not quantified anywhere found.

### Cited Findings
- RepoLaunch 2026 build failures (Linux): command timeout/OOM dominates for C/C++ (61.2% of failures) and Go (36.7%); "repo not at production state" is common for JS/TS (20.7%); failed regression-test execution highest for JS/TS (33.2%). Windows build: dependency resolution 20.2%, timeout/OOM 20.4%, failed test execution 19.7%. Management stage: log-parse failure is the largest category in most languages; on Windows, failing to derive the rebuild command (30.8%). — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2)
- RepoLaunch: giving unlimited time/RAM/CPU raised build success from 77.8% to 84.4%, quantifying the resource-limit share. A NeurIPS 2026 slide deck describes Rust as the hardest language and Windows as the hardest OS. — [RepoLaunch paper](https://arxiv.org/html/2603.05026v2); [NeurIPS 2026 slides](https://neurips.cc/media/neurips-2026/Slides/151672_e8oq2x5.pdf)
- Repo2Run's 59 failures: runtest timeout 24 (40.7%), hardware insufficiency 21 (35.6%), dependency-install timeout 8 (13.5%), repository defects 5 (8.5%), missing token 1 (1.7%). Success was lowest in AI/ML repos (82.8%) vs software-engineering repos (95.9%). — [Repo2Run paper](https://arxiv.org/html/2502.13681v4)
- EnvPilot failure taxonomy (25 failures of 112): toolchain and runtime issues 60%, platform/system constraints 16%, native dependency failures 16%, repo-config mismatch 8%. — [EnvPilot paper](https://arxiv.org/html/2609.07357v1)
- EnvBench: causes of failing scripts are missing system dependencies, Python/Java version mismatches, and use of tools unavailable on the system; zero-shot and Installamatic most often fail on unavailable tools; the Bash Agent sometimes repeats the same failing action. — [EnvBench paper](https://arxiv.org/html/2503.14443v1)
- ExecutionAgent: repeating mistakes (e.g. `sudo` when unavailable); installing a new Node/gcc version without making it the default; multi-module projects where one failing module halts the rest; missing binaries such as headless Chromium; flaky tests; git submodules (only 2/9 tested) and C/C++ hardest; Java easiest. — [ExecutionAgent paper](https://arxiv.org/html/2412.10133)
- SetupBench (OpenHands): three named failure modes - incomplete development-tooling installation, hallucinated task constraints, and non-persistent environment modifications (changes that do not survive into a new shell/session); 38-89% of agent actions were unnecessary relative to optimal human behaviour. — [SetupBench abstract](https://arxiv.org/abs/2507.09063v1)
- Dependency drift for historical commits: SWE-bench-Live redirects pip to a proxy serving only package versions released on or before the base commit timestamp and reports this "significantly improves setup success rates" (no figure). — [SWE-bench-Live paper](https://arxiv.org/html/2505.23419)
- Repo2Run pins: its Dockerfile synthesizer replaces unpinned packages with the exact installed versions so the frozen recipe does not drift later. pipreqs-style inference failed on 63.1% of repos from version conflicts at download. — [Repo2Run paper](https://arxiv.org/html/2502.13681v4)
- Network: SWE-rebench V2 allows network at install time but expects runtime test execution not to need network-dependent installs; it lists flaky tests and external dependencies as reward-noise sources, and repos needing multiple services/external infrastructure as unpackageable in one container. — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- Cursor autoinstall handles missing external services by mocking (MinIO for S3, fake database tables, placeholder files, sidecar containers) rather than requiring network. — [Cursor blog](https://cursor.com/blog/bootstrapping-composer-with-autoinstall)
- SWE-rebench V2: longer context can cause loops or focus on irrelevant details; stale build artifacts in C/C++; setup inferred at the latest snapshot may not hold at other commits. — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- Multi-Docker-Eval: weakest languages are C/C++, Java, Rust, PHP (Java fail-to-pass 8.57-14.29% across models); Go strongest (54.50%); hard instances retain only 0.24-0.73 of easy-instance success depending on framework. — [Multi-Docker-Eval paper](https://arxiv.org/html/2512.06915v3)
- SWE-Factory: Java is both lowest-yield (11.8-28.5% valid) and most expensive; "error2pass" (pre-patch collection errors) contaminates fail-to-pass sets. — [SWE-Factory paper](https://arxiv.org/html/2506.10954v2)

### Inferences
- For a Python-heavy, historical-commit, network-isolated pipeline like Fleet, the literature points at four specific risks in descending documented importance: (a) timeouts/RAM limits during install and test (largest single category in two papers); (b) interpreter/toolchain version selection (60% of EnvPilot failures; Repo2Run changed base image in 13% of successes); (c) dependency drift, addressable with a date-bounded index proxy plus freezing resolved versions into the image; (d) tests that touch the network or external services, which no surveyed system verifies by actually running tests with network disabled - Fleet's network-isolated validation run is stricter than published practice.
- "Non-persistent modifications" (SetupBench) and "new version installed but not made default" (ExecutionAgent) are the same class: state that exists in the agent's shell but not in the frozen image. Replaying the recorded recipe in a fresh container (Repo2Run's synthesizer, RepoLaunch's rebuild-command verification) is the documented countermeasure.
- Published benchmarks are biased toward recent repositories (Repo2Run: created in 2024; EnvBench: active since Jan 2024; Multi-Docker-Eval: PRs after July 2025), so reported success rates are likely optimistic for multi-year-old commits where EOL interpreters, yanked packages and sdist-only native builds appear.

### Gaps
- No quantitative evidence found on failures specific to old Python versions (e.g. 2.7/3.5/3.6 base images, EOL distro apt repositories) or on yanked/removed PyPI releases; the date-bounded index is the only published mitigation and its effect is unquantified.
- No study found that measures how many repos' tests fail specifically because of network isolation at test time.
- Native-dependency failures are reported only as a coarse category (16% in EnvPilot; "missing system dependencies" in EnvBench) without a breakdown by library or build system.
- SetupBench's per-model overall success numbers and its detailed failure examples were not retrieved (full text not read).
