# Architecture of pipelines that turn repositories into validated coding tasks (state as of 2026-11-15)

Method note for the report writer: unless marked "(secondary)" or "(search snippet)", every number below was extracted from the primary page cited (arXiv HTML, official GitHub README, or vendor page) through a fetch-and-summarise tool, so the wording is paraphrased and long papers were read only to roughly the first 100k characters (late appendices were not read). Two OpenAI pages returned HTTP 403 and could not be read directly; facts from them are marked. Dates of each source are given because most papers are from 2024-2025 and only a few are 2026.

## 1. Pipeline stages per system, and where agents/LLMs are used

### Takeaway
The field moved in three steps: (a) 2023-2024, deterministic mining plus manual environment building (SWE-bench, SWE-Gym, Multi-SWE-bench, SWE-bench Pro, Commit0); (b) 2025, an LLM or agent only for environment setup and optionally issue text, with execution as the gate (SWE-rebench, SWE-bench-Live/RepoLaunch, SWE-Factory, SWE-smith, R2E-Gym); (c) 2026, agents build the environment and the verifier per repo/PR, wrapped by LLM "anti-hack" checks and LLM judge ensembles (SWE-rebench V2, SWE-Universe, Scale-SWE, HF Repo2RLEnv Tasksmith). In every system the acceptance decision is still a measured fail-to-pass run; LLMs propose setups, write text, and filter, but do not accept.

Per-system details:

- SWE-bench (Oct 2023): three stages: scrape PRs from 12 popular Python repos; attribute filter (merged, resolves an issue, changes test files); execution filter (at least one fail-to-pass test, no install/runtime errors; also drops ImportError/AttributeError pre-fix cases). Environments were created manually per release version; no LLM use in construction — [SWE-bench paper](https://arxiv.org/html/2310.06770v3)
- SWE-Gym (Dec 2024): repo selection via SEART (358 Python repos), SWE-bench extraction script, semi-automatic version tagging, manual dependency configuration for 11 repos, SWE-bench-style execution validation. No LLM in construction — [SWE-Gym paper](https://arxiv.org/html/2412.21139v2)
- Multi-SWE-bench (Apr 2025): five phases: repo selection (>500 stars, CI config, latest commit builds), PR crawling (issue-linked, modifies tests, merged), environment determination (engineers write and iteratively fix Dockerfiles), semantic filtering using three logs (run.log at base, test.log with test patch, fix.log with test+fix patch), manual verification. No LLM in construction — [Multi-SWE-bench paper](https://arxiv.org/html/2504.02605v1)
- SWE-bench Pro (Sep 2025): consecutive commit pairs mined for a fail-to-pass transition; humans write problem statement, requirements and interface; engineers build Docker environments; automated repeated gold-test runs then a human pass over each F2P test. Three splits: public (11 copyleft repos), held-out (12 copyleft repos, private), commercial (18 private startup repos) — [SWE-bench Pro paper](https://arxiv.org/html/2509.16941v1)
- Commit0 (Dec 2024): library selected by criteria (>95% Python, pytest, >90% unit-test coverage, dedicated docs site, tests under 30 min on one CPU, no GPU); starter repo made by AST transform replacing public function bodies with `pass` and deleting private functions; docs crawled to PDF as the specification; per-library Docker image. No LLM in construction — [Commit0 paper](https://arxiv.org/html/2412.01769v1)
- SWE-rebench V1 (May 2025): four stages: preliminary collection, automated installation configuration (Qwen2.5-72B-Instruct emits up to three candidate JSON install recipes per task, non-interactive), execution-based verification, automated quality assessment (fine-tuned Qwen2.5-72B). The authors tested an interactive agent and rejected it at the time as far more resource-intensive for similar success on an 18-task probe — [SWE-rebench paper](https://arxiv.org/html/2505.20411v2)
- SWE-rebench V2 (Feb 2026) reversed that choice: setup is done by mini-SWE-agent v1.14.4 with Qwen3-Coder-480B, run once per repository on its latest mined snapshot and reused for all of that repo's tasks; the same model writes base Dockerfiles per toolchain version and log parsers (regenerated from successful traces, up to five iterations). Collection and execution validation are deterministic; an ensemble of three LLM judges (gpt-oss-120b, GLM-4.7, DeepSeek-V3.2) filters issue clarity; gpt-oss-120b adds diagnostic labels and "interface" descriptions; a separate LLM step writes synthetic problem statements for PR-only tasks — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- SWE-bench-Live (May 2025): three stages: crawl issue-PR pairs, RepoLaunch environment setup, validation by repeated test runs. RepoLaunch steps: LLM lists relevant files (CI configs, README); LLM picks a base image from a candidate list; a ReAct setup agent works in a persistent bash session; a verify agent writes and runs the test command (must give per-test status) and reports problems back; the container is committed as an image. A "time-machine" pip proxy restricts installs to package versions released before the base commit — [SWE-bench-Live paper](https://arxiv.org/html/2505.23419v2)
- RepoLaunch standalone paper (first submitted 5 Mar 2026, v3 dated 3 Oct 2026): generalised to multiple languages and operating systems; the abstract states humans are needed only at task design and that the pipeline has been adopted by several other benchmark/training works — [RepoLaunch abstract](https://arxiv.org/abs/2603.05026)
- SWE-Factory (Jun 2025, v3): SWE-Builder has four agents: Repository Explorer (reads configs/docs with browse and search tools), Environment Manager (writes/updates Dockerfile), Test Manager (writes the evaluation script), Test Analyst (builds, runs with the gold patch, analyses logs and routes fixes). A memory pool stores each successful Dockerfile and script and retrieves the nearest-version setup from the same repo for new issues. Grading uses an exit-code marker printed by the script instead of log parsers — [SWE-Factory paper](https://arxiv.org/html/2506.10954v3)
- R2E-Gym / SWE-GEN (Apr 2025): commit curation with rule-based plus LLM-judge filters (at most 5 non-test files, 100 edited lines, 2,000-character patch); semi-manual Docker environment build with search-based dependency resolution; F2P tests taken from existing tests or generated by an Agentless-like LLM step that sees the ground-truth patch; patch minimisation; LLM backtranslation of an issue from commit message, code patch and F2P test output — [R2E-Gym paper](https://arxiv.org/html/2504.07164v1)
- SWE-smith (Apr 2025): SWE-agent (claude-3-5-sonnet, $2 and 150-call limit per repo) installs each repo and runs tests; a human reviews and requires >80% of existing tests to pass; four bug strategies (LM Modify/Rewrite with o3-mini, procedural AST modification without LM, Combine of validated bugs, PR Mirror where an LM undoes a merged PR); execution validation with a two-minute cap; LM-written issue text; one Docker image per repository rather than per task — [SWE-smith paper](https://arxiv.org/html/2504.21798v2)
- SWE-Synth (Apr 2025): pick a component (uniform or coverage-weighted), mask its body, have Qwen2.5-Coder-32B re-implement it in a single generation, keep variants that compile and fail a test, then run a MoatlessTools repair agent (three rounds) and keep the successful trajectory's patch as ground truth; the failing test log is the problem statement — [SWE-Synth paper](https://arxiv.org/html/2504.14757v1)
- SWE-Flow (Jun 2025): trace unit tests to build a runtime dependency graph, derive an ordered development schedule, and for each step emit a partial codebase (target bodies removed), a development document and the ground-truth diff. An LLM (Qwen2.5-Coder-32B) writes only docstrings and development documents — [SWE-Flow paper](https://arxiv.org/html/2506.09003v1)
- SWE-Universe (Feb 2026): an LLM splits each PR into test and fix patches; a mini-swe-agent-based builder with tools `bash`, `switch-to-resolved` and `switch-to-bug` writes an `evaluation.sh` verifier and self-checks it by toggling repo state, up to about 100 turns; an LLM hack detector runs inside the loop; a quality-judge agent scores tasks. The builder model is a custom fine-tuned model trained by rejection sampling on successful non-hacked trajectories — [SWE-Universe paper](https://arxiv.org/html/2602.02361v1)
- Scale-SWE (Feb 2026): sandboxed multi-agent workflow with three agents: Environment Builder, Unit-test Creator, Problem Statement Writer (search snippet of the abstract; full paper not read) — [Scale-SWE abstract](https://arxiv.org/abs/2602.09892)
- Hugging Face Repo2RLEnv (README as of v0.9.6, 11 Nov 2026): turns repos and related material into Harbor tasks (`instruction.md`, `task.toml`, `environment/`, `tests/`, `solution/`). 24 generators grouped as repository repair (Tasksmith, `pr_runtime`, `commit_runtime`, `cve_patches`, `trajectory_to_env`, `swe_smith`, `swe_next`, `r2e_gym`), implementation/reconstruction (`code_instruct`, `equivalence_tests`, `r2e`, `swe_flow`, `swe_gen`, `codemidas`), patch similarity (`pr_diff`), terminal tasks, and reasoning/optimisation. Tasksmith is an agent that investigates a merged PR, bootstraps the environment on a remote worker, designs the instruction and a private verifier, builds the task with the merged code as reference solution, then reviews and repairs until controls pass; it orchestrates Pi or OpenCode agents with LangGraph on Daytona or Modal. Native runtime pipelines run on local Docker — [Repo2RLEnv README](https://github.com/huggingface/repo2rlenv)
- Repo2RLEnv `pr_runtime` triggers a cache lookup and runs bootstrap only on a miss, so environment construction happens once per (repo, ref) (search snippet of PyPI page) — [repo2rlenv on PyPI](https://pypi.org/project/repo2rlenv/)
- Nemotron-CORTEXA (ICML 2025) is an issue-resolution agent, not a task-generation pipeline: its training data is built from the SWE-bench training split plus retrieval tasks from public code-understanding datasets; it reports 68.2% on SWE-bench Verified at $3.28 per problem — [NVIDIA CORTEXA page](https://research.nvidia.com/labs/adlr/cortexa)
- NVIDIA's related datasets are trajectory corpora built on other people's environments: Nemotron-SWE-v1 has 59k OpenHands trajectories with issue statements sourced from SWE-Gym and R2E-Gym-Subset and regenerated with Qwen3-Coder-480B (search snippet of dataset card) — [Nemotron-SWE-v1 card](https://huggingface.co/datasets/nvidia/Nemotron-SWE-v1)

### Inferences
- The agent's stable niche across systems is environment setup plus test-command/verifier authoring, scoped per repository (rebench V2, SWE-smith) or per PR (SWE-Universe, SWE-Factory, RepoLaunch). Fleet's single "reviewer" agent is an unusual placement: comparable systems put the agent before execution (to make the run possible) and use cheap non-agentic LLM judges after execution.
- Three different scoping choices for environment reuse exist: per repo snapshot (rebench V2, SWE-smith), per version with memory of previous successes (SWE-Factory, SWE-bench), and per PR (SWE-Universe). Per-repo reuse is cheapest but loses older commits whose dependencies drifted.
- Two verifier styles exist: log parsers giving per-test status (SWE-bench lineage, rebench, RepoLaunch) and exit-code scripts (SWE-Factory, SWE-Universe). Exit-code scripts remove parser maintenance but give no per-test F2P/P2P lists and invite shallow verifiers, which is why SWE-Universe needed a hack detector.
- Repo2RLEnv is the closest published analogue to Fleet (Harbor output, merged-PR input, oracle/no-op controls, review-and-repair loop) and already wraps most of the other systems as generators.

### Gaps
- Scale-SWE internals (validation gate, yields per stage) were not read beyond the abstract snippet.
- RepoLaunch 2026 paper: only the abstract was read; agent design changes and per-language results are unknown.
- Repo2RLEnv native pipelines: the README does not say which steps of `pr_runtime`/`commit_runtime` call an LLM; the documentation site returned 404 at the guessed URL.
- The LLM used inside the original RepoLaunch is not named in the SWE-bench-Live paper.

## 2. Yields, cost per task, and what dominates rejection

### Takeaway
End-to-end yield from raw PRs is a fraction of a percent to a few percent; the two dominant losses are "no issue link / no test change" at the metadata stage and environment setup at the execution stage. Where costs are published they are cents per task for LLM spend (SWE-Factory about $0.05, SWE-smith about $0.02-0.03 per candidate); most 2026 large-scale papers publish no dollar cost.

### Cited Findings
- SWE-bench (2023): 93,139 PRs crawled, 11,407 candidate tasks, 2,294 final (about 2.5% of PRs, about 20% of candidates); the paper says execution filtering "generally removes half" of candidates — [SWE-bench paper](https://arxiv.org/html/2310.06770v3)
- SWE-Gym (2024): 64,689 raw instances from 358 repos; 2,438 validated instances from the 11 repos that were manually configured; about 200 human hours and 10,000 CPU core hours; images total 6 TB — [SWE-Gym paper](https://arxiv.org/html/2412.21139v2)
- SWE-rebench V1 (2025): about 450,000 issue-linked PRs from over 30,000 repos, about 153,400 candidates after preliminary filtering, 21,336 validated tasks from 3,468 repos (about 14% of candidates). The LLM recipe approach produced a working recipe for at least one task in 31% of repositories — [SWE-rebench paper](https://arxiv.org/html/2505.20411v2)
- SWE-rebench V2 funnel (2026): 29,511,758 raw PRs / 145,306 repos; 8,593,722 PRs with tests; 805,598 linked to an issue and tests; 583,809 after repo filtering (21,692 repos); 41,349 with F2P (4,006 repos); 32,079 after the issue-clarity filter (3,617 repos) — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- SWE-rebench V2 setup ablation on 103 tasks, 10 runs each: non-interactive pipeline pass@1 12.1 / pass@10 15.7; agent with Qwen3-480B at 32k context 25.8 / 58.8; at 128k context 27.1 / 62.7. The production run used one attempt per repo; roughly 80% of repos fail on a single attempt. No dollar cost is reported — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- SWE-rebench V2 repo pre-filtering keeps about 20% of repos but about 80% of tasks, cutting setup work about 5x (Python: 2,144 of 10,548 repos keep 152,161 of 184,558 tasks) — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- SWE-bench-Live (2025): 8,577 repos from the initial query, 3,316 after activity filters, 2,609 after licence filter; final 1,319 instances from 93 repos. Neither the RepoLaunch success rate nor cost per instance is reported in the paper — [SWE-bench-Live paper](https://arxiv.org/html/2505.23419v2)
- RepoLaunch (2026 abstract): 78% build success, stated as 18% better than the prior system — [RepoLaunch abstract](https://arxiv.org/abs/2603.05026); a search summary of the same paper reported "approximately 70% across nine languages and two platforms", which conflicts and was not resolved — [RepoLaunch PDF](https://arxiv.org/pdf/2603.05026)
- SWE-Factory v3 (2025), 671 issues from 12 repos in 4 languages: GPT-4.1 mini 50.2% valid (337), 26.3 min and $0.047 per instance; Kimi-K2 47.8% (321), $0.056; DeepSeek-V3 42.0% (282), $0.037. Earlier v2 abstract reported 269 valid at $0.045 with GPT-4.1 mini (v2 figure from search snippet) — [SWE-Factory paper v3](https://arxiv.org/html/2506.10954v3)
- SWE-Factory ablations: removing execution feedback collapses valid rate to 0.3-2.7%; removing the memory pool costs 4.3-6.1 points; removing the Repository Explorer costs 7-8 points for two of three models while halving cost ($0.047 to $0.021) — [SWE-Factory paper v3](https://arxiv.org/html/2506.10954v3)
- SWE-smith (2025) yield per strategy (share of candidates that break at least one test) and cost per candidate: Combine 96.9% / 0 cents; LM Modify 56.0% / 0.38 cents; LM Rewrite 35.0% / 3.93 cents; PR Mirror 33.8% / 5.53 cents; Procedural 40.2% / 0 cents; total 50.1% / 2.32 cents. Total spend $1,360 (about $1,000 bug generation, $160 automatic installation, $200 issue text for 10k bugs); about 20 human hours, 17 of 145 repos dropped at install review; environments total 295 GB versus 6 TB for SWE-Gym and 4 TB for R2E-Gym — [SWE-smith paper](https://arxiv.org/html/2504.21798v2)
- SWE-Synth (2025): 21,804 variants generated, 9,459 kept (about 43%); usable-variant rate depends on rewriter size (9% for a 0.5B model, about 57% for 3B and 14B) — [SWE-Synth paper](https://arxiv.org/html/2504.14757v1)
- SWE-Flow (2025): 74 of 150 selected projects passed all unit tests after Docker setup; no cost figure — [SWE-Flow paper](https://arxiv.org/html/2506.09003v1)
- Multi-SWE-bench (2025): 2,456 instances passed execution filtering; 1,632 survived human verification (about 66%) — [Multi-SWE-bench paper](https://arxiv.org/html/2504.02605v1)
- SWE-Universe (2026): about 33.3M PRs, about 1M candidates after heuristics, 75.9% non-hacked build success giving 717,122 issue-based environments plus 90,571 from 2025 PRs without issues; 807,693 total. Self-verification raised held-out success from 82.6% to 94%. No cost per instance is given — [SWE-Universe paper](https://arxiv.org/html/2602.02361v1)
- Scale-SWE (2026): 6 million PRs across 5,200 repos processed, 100,000 verified instances (about 1.7%); expert audit of a sample found 94% valid (search snippet of abstract) — [Scale-SWE abstract](https://arxiv.org/abs/2602.09892)
- Repo2RLEnv: an index of the project docs describes yield as "typically low (~5-25%)" because a verifiable fail-to-pass oracle is required (search snippet of a third-party docs index, not the docs themselves) — [docs index entry](https://docsearch.algolia.com/mcp/docs/repo/huggingface/repo2rlenv). The README reports 21 published datasets with 1,930 tasks and a 50-task verified Tasksmith cohort from five HF libraries, but no per-task cost — [Repo2RLEnv README](https://github.com/huggingface/repo2rlenv)
- A July 2026 paper, Change2Task, appeared in search with a table giving "cost per finalized task $2.13 vs $1.90" (search snippet only; paper not read, context of the comparison unknown) — [Change2Task PDF](https://arxiv.org/pdf/2607.28591)

### Inferences
- Rejection order by magnitude in mined pipelines: (1) PR has no test change (about 71% lost in rebench V2); (2) no linked issue (about 91% of the remainder); (3) environment setup / no F2P (about 93% of repo-filtered PRs in rebench V2 with one setup attempt per repo); (4) clarity filter (about 22%). Systems that drop the issue requirement (R2E-Gym, SWE-Universe 2025 PRs, rebench V2 PR set, Fleet's commit mining) recover an order of magnitude of candidates but must then synthesise a problem statement.
- Setup retries are the cheapest yield lever on record: pass@10 is about 2.3x pass@1 in rebench V2, and SWE-Universe's self-verification loop added about 11 points.
- Agentic per-PR task building costs dollars per task (Change2Task snippet, unverified), versus cents for single-purpose LLM pipelines; nobody at the 100k+ scale publishes cost, and SWE-Universe addressed cost by fine-tuning its own builder model.
- Storage is a real cost axis: per-task images reach terabytes; per-repo images (SWE-smith) are about 20x smaller.

### Gaps
- No published cost per task for SWE-rebench V1/V2, SWE-bench-Live, R2E-Gym, SWE-Universe, Scale-SWE or Repo2RLEnv.
- No system publishes a breakdown of environment failures by cause (dependency drift, system packages, network, timeouts); only qualitative mentions.
- The RepoLaunch 78% versus about 70% discrepancy needs the full paper.

## 3. Quality assurance after execution validation

### Takeaway
Post-execution QA has become a standard layer: flakiness reruns, LLM judges for issue clarity (validated against SWE-bench Verified human labels, with high precision but very low recall), diagnostic labels rather than hard rejects, leak checks on synthetic problem statements, verifier anti-hack checks, and oracle/no-op controls. Published accuracy of LLM judges is modest (67-81%), and later audits show these layers did not prevent large flaw rates in human-curated benchmarks.

### Cited Findings
- Flakiness: SWE-rebench V1 runs tests multiple times and excludes instances failing in any run; SWE-bench-Live keeps only instances consistent across repeated runs (count not stated); SWE-bench Pro runs each test set 3 times and drops inconsistent tests — [SWE-rebench](https://arxiv.org/html/2505.20411v2); [SWE-bench-Live](https://arxiv.org/html/2505.23419v2); [SWE-bench Pro](https://arxiv.org/html/2509.16941v1)
- Regression semantics: Multi-SWE-bench discards PRs with any ANY->PASSED->FAILED transition or ambiguous PASSED->NONE/SKIPPED->FAILED transitions across its three logs, and requires at least one ->FAILED->PASSED — [Multi-SWE-bench paper](https://arxiv.org/html/2504.02605v1)
- SWE-rebench V1 quality labels: Qwen2.5-72B fine-tuned on SWE-bench Verified annotations (over 3,800 examples) predicts task complexity (81% accuracy), test-patch correctness (67%) and issue clarity (79%); labels are shipped as metadata — [SWE-rebench paper](https://arxiv.org/html/2505.20411v2)
- SWE-rebench V2 clarity filter: three judges must all rate the issue adequate. Against 1,699 human-annotated SWE-bench Verified instances the chosen prompt (includes patch and test patch) reaches precision 0.83 but recall 0.10; strict consensus reaches precision 0.88 and recall 0.06; score averaging gives the best F1 (0.43) but was not adopted. The filter removed about 22% of F2P-valid tasks — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- SWE-rebench V2 diagnostic labels (LLM-assigned): B1 TEST_SUITE_COUPLING (regressions in unrelated paths), B2 IMPLICIT_NAMING (tests expect names the statement does not give; mitigated by injecting generated "interface" descriptions), B3 EXTERNAL_DEPENDENCY (statement links to outside resources). Suggested use is subset selection, not deletion — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- SWE-rebench V2 PR-derived tasks get LLM-written problem statements with post-processing to flag solution leakage; the leakage rate is not reported — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- SWE-Universe: an LLM hack detector inspects each `evaluation.sh` inside the build loop and rejects verifiers that grep or string-match source instead of running tests; on a 320-PR benchmark the hacked share was 4.06 points for its own builder and over 7 points for Claude Opus 4.5 (85.00% with hacks vs 77.81% without). A quality-judge agent reached 78.72% accuracy on a human-labelled set — [SWE-Universe paper](https://arxiv.org/html/2602.02361v1)
- SWE-Factory: exit-code F2P validation compared with manual inspection on 1,201 instances gave 923 TP, 0 FP, 16 FN (v3). The 16 misses came from generated scripts: 12 from `set -e` exiting before the marker line, 4 from a wrong identifier. The v2 abstract reported precision 0.92 and recall 1.00, so the figures changed between versions (v2 from search snippet) — [SWE-Factory paper v3](https://arxiv.org/html/2506.10954v3)
- SWE-Factory fixes a mining-level defect: binary test files arrive empty in API-collected patches; without detection and re-download, F2P fell to 0% on the 44 affected instances; up to 30% of issues in Pillow were affected — [SWE-Factory paper v3](https://arxiv.org/html/2506.10954v3)
- R2E-Gym generated tests: for most problems under 20% of generated tests were distinguishing; some failed ground-truth patches ("toxic" tests, up to 10% of a problem's tests) — [R2E-Gym paper](https://arxiv.org/html/2504.07164v1)
- SWE-smith difficulty model: 75.3% accuracy; expert resolve rate by label easy 58.6%, medium 41.0%, hard 17.0%; difficulty did not predict training usefulness — [SWE-smith paper](https://arxiv.org/html/2504.21798v2)
- Human verification baselines: Multi-SWE-bench used 68 annotators, dual annotation, a 14-engineer internal team and an 80% accuracy bar, with difficulty from estimated fix time (easy <=15 min, medium 15 min-1 h, hard >=1 h); SWE-bench Verified (Aug 2024) had 93 developers annotate 1,699 samples for underspecified issues and F2P tests that reject valid solutions, keeping 500 — [Multi-SWE-bench paper](https://arxiv.org/html/2504.02605v1); [SWE-bench Verified page](https://swebench.com/verified) (Verified numbers from search snippet; OpenAI post returned 403)
- Repo2RLEnv controls: oracle (reference solution) must score 1 and a no-op must score 0; failing tasks go through review-and-repair; tasks carry an evaluation label in `task.toml`; `pr_diff` tasks need an LLM correctness judge and are left ungraded without one. Release notes: v0.9.4 (23 Oct 2026) "task quality review", v0.9.5 (4 Nov 2026) "stricter test grading", v0.9.6 (11 Nov 2026) "isolated grading". The README says a generated task "is a starting point, not a guarantee" — [Repo2RLEnv README](https://github.com/huggingface/repo2rlenv)
- Contamination control: SWE-rebench marks leaderboard results where issues predate a model's release; SWE-bench-Live restricts to recent issues with planned monthly refresh; SWE-bench Pro uses copyleft and private repos plus a private held-out split; R2E-Gym ships a subset with no repo overlap with SWE-bench test; SWE-Universe filters PRs overlapping downstream benchmarks — [SWE-rebench](https://arxiv.org/html/2505.20411v2); [SWE-bench-Live](https://arxiv.org/html/2505.23419v2); [SWE-bench Pro](https://arxiv.org/html/2509.16941v1); [R2E-Gym](https://arxiv.org/html/2504.07164v1); [SWE-Universe](https://arxiv.org/html/2602.02361v1)

### Inferences
- Checks Fleet may be overlooking, each with a published precedent: (1) a no-op control alongside the oracle control (Repo2RLEnv); (2) repeated before/after runs with exclusion on any inconsistency; (3) explicit rejection of P2P regressions and ambiguous skip transitions (Multi-SWE-bench); (4) binary test file handling in patches (SWE-Factory); (5) time-pinned dependency resolution (RepoLaunch proxy); (6) implicit-naming detection, i.e. tests that require identifiers absent from the statement, the same flaw class OpenAI later found in Verified; (7) removal of git history or future commits that contain the fix (see section 5); (8) verifier-quality checks if any verifier is agent-written.
- LLM clarity judges are tuned for precision at the cost of recall (0.06-0.10), so they remove only a small part of truly underspecified tasks. They work as a cheap coarse filter and as metadata, not as assurance. This is consistent with Fleet's rule that models do not decide acceptance, but it also means measured runs alone do not catch specification/test misalignment.
- No surveyed pipeline runs a test-adequacy check that tries alternative correct or incorrect patches against F2P tests (mutation-style or multi-solution checks) at scale; the closest are R2E-Gym's "distinguishing test" analysis and human annotation.

### Gaps
- No published accuracy for rebench V2's diagnostic labeller, for R2E-Gym's commit judge, or for any leak detector.
- Repo2RLEnv's evaluation-label taxonomy and what "task quality review" checks were not retrievable.
- Number of validation reruns is unspecified in SWE-rebench and SWE-bench-Live.

## 4. Synthesised versus mined tasks: realism and training value

### Takeaway
Four synthesis families exist: bug injection (SWE-smith, SWE-Synth), commit backtranslation with generated tests and issues (R2E-Gym/SWE-GEN), test-driven decomposition (SWE-Flow), and function/library removal (Commit0). The consistent published result is that synthetic tasks train agents about as well as mined ones per trajectory and scale far more cheaply, with the caveat that the closer the bug is to a real change (PR inversion), the better it trains, and that these comparisons are small single-run studies.

### Cited Findings
- SWE-smith training value per bug type (1,000 instances each, SWE-bench Verified): PR Mirror 9.2%, LM Rewrite 8.8%, Procedural 8.6%, LM Modify 5.7% — [SWE-smith paper](https://arxiv.org/html/2504.21798v2)
- SWE-smith issue text ablation: LM-generated issues (7.7%) performed like original issues (7.8%); fixed templates were worst (6.4%); giving the F2P test as the statement leaked the evaluation criteria and made the model skip writing a reproduction script — [SWE-smith paper](https://arxiv.org/html/2504.21798v2)
- SWE-smith: performance scales roughly logarithmically with number of repositories; repeatedly solved easy instances hurt, so trajectories are capped at 3 per instance; SWE-agent-LM-32B trained on 5,016 trajectories reached 40.2% on SWE-bench Verified — [SWE-smith paper](https://arxiv.org/html/2504.21798v2)
- R2E-Gym: with 400 trajectories each, synthetic (backtranslated) issues gave 27.8% and real GitHub issues 28.0% pass@1; the commit-based approach yields "2.5 times more problems" than issue-based collection; 32B model reached 34.4% on Verified versus 20.6% for SWE-Gym-trained — [R2E-Gym paper](https://arxiv.org/html/2504.07164v1)
- SWE-Synth: at an equal 230-instance budget SWE-Gym data gave 12.00% and SWE-Synth 11.67% on SWE-bench Lite; in a human study 11 participants distinguished real from synthetic bugs with 55.17% accuracy; using the reverse diff as the ground-truth fix trained far worse (0.67%) than using agent-rollout fixes (15.33%); function-level bugs trained better than class-level (12.00% vs 9.67%) — [SWE-Synth paper](https://arxiv.org/html/2504.14757v1)
- SWE-Flow: produces 16,061 training and 2,020 test instances from 74 projects; fine-tuning on it raised per-project pass rates on its own benchmark (e.g. 46.0% to 76.0% on one project); tracing is unreliable for asyncio and multi-process code — [SWE-Flow paper](https://arxiv.org/html/2506.09003v1)
- Commit0: models pass 6% of unit tests across all libraries with no feedback (17% on the lite set, 26% with test feedback); 10-gram overlap analysis found models either fully memorise functions or write clearly different code, with short functions memorised more often; web retrieval of the original repos was restricted — [Commit0 paper](https://arxiv.org/html/2412.01769v1)
- SWE-Gym (mined) caveats relevant to training: on-policy self-improvement reduced OpenHands performance (15.3% to 8.7% on Lite); the task distribution is long-tailed (pandas nearly one third); easy-task bias required per-instance capping — [SWE-Gym paper](https://arxiv.org/html/2412.21139v2)
- Mined data at 2026 scale: SWE-Universe trained on 500K trajectories, moving its model from 50.3% to over 61% on SWE-bench Verified, and reports 75.3% for Qwen3-Max-Thinking; Scale-SWE reports 22% to 64% for Qwen3-30B after distilling 71,498 trajectories (Scale-SWE from search snippet) — [SWE-Universe paper](https://arxiv.org/html/2602.02361v1); [Scale-SWE abstract](https://arxiv.org/abs/2602.09892)
- Repo2RLEnv packages both families as interchangeable generators (`swe_smith`, `r2e_gym`, `swe_gen`, `swe_flow`, `commit_runtime`, `pr_runtime`, `cve_patches`) emitting the same Harbor format — [Repo2RLEnv README](https://github.com/huggingface/repo2rlenv)

### Inferences
- For training, synthetic generation over a small set of well-built per-repo environments is the cheapest path to volume, and mined PR inversions are the highest-value synthetic type. Fleet's mined fail-to-pass tasks sit at the high-realism end; a PR-Mirror-style or procedural injector could reuse the same built containers to multiply output.
- For benchmarking, synthetic tasks are not used by any of the surveyed evaluation sets; all benchmarks mine real changes, and their problems come from specification/test mismatch, not from lack of realism.
- Issue text matters less than expected for training (LM-written equals original) but its content matters for leakage: never expose F2P test content in the statement.

### Gaps
- No head-to-head study of synthetic versus mined data at the 2026 scale (100k+ tasks, RL rather than SFT) was found.
- Training-value evidence is mostly measured on SWE-bench Verified, which OpenAI stopped reporting in Feb 2026 because of contamination and test flaws, so these deltas are weaker evidence than they look.
- No realism study exists for SWE-smith or R2E-Gym comparable to SWE-Synth's human study.

## 5. What went wrong or was retired

### Takeaway
The main documented failures are not in execution validation but in what it cannot see: tests that reject correct solutions or demand unstated names, underspecified or over-prescriptive problem statements, solution leakage (issue text, git history), contamination, and agent-written verifiers that do not run code. SWE-bench Verified was dropped by OpenAI in February 2026, and its recommended successor SWE-bench Pro was rated "Flawed" by Epoch AI in September 2026.

### Cited Findings
- SWE-Bench+ (Oct 2024) on original SWE-bench with SWE-Agent+GPT-4: 32.67% of resolved instances had the solution stated in the issue or comments; 31.08% passed with incorrect or incomplete patches due to weak tests; filtering dropped the resolve rate from 12.47% to 3.97% — [SWE-Bench+ paper](https://arxiv.org/html/2410.06992v2) (numbers from search snippet of that page)
- OpenAI (23 Feb 2026) stopped reporting SWE-bench Verified: an audit of 138 problems that o3 did not consistently solve over 64 runs, each reviewed by at least six engineers, found 59.4% with material flaws in tests or problem description; the post has a section on tests that are too narrow or too wide and cites training-data contamination; it recommended SWE-bench Pro in the interim (page returned 403; details from search snippets, including a secondary summary stating 35.5% of flawed cases relied on specific function names not in the prompt and 18.8% checked unrelated features) — [OpenAI post](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)
- Epoch AI review of SWE-bench Pro, dated 1 Sep 2026, verdict "Flawed": Jonathan Gabor (24 Feb 2026) audited 100 random public tasks and found issues in 83, mainly "requirements inflation" (requirements containing implementation details that are not tested); Datacurve (26 May 2026) LLM-assisted audit found 24% false negatives and 8.5% false positives; OpenAI (8 Jul 2026) estimated 30% of tasks broken, with categories misleading prompts, overly strict tests, underspecified prompts and low-coverage tests; Poolside documented reward-hacking behaviours in the task environment; no Scale AI response was listed — [Epoch AI review](https://epoch.ai/benchmarks/swe-bench-pro/review)
- Secondary reports (not confirmed in a primary source) say Datacurve also found agents reading the fix from git history retained in SWE-bench Pro containers, and that OpenAI withdrew its Pro recommendation in July 2026 — [VentureBeat](https://venturebeat.com/ai/deepswe-blows-up-the-ai-coding-leaderboard-crowns-gpt-5-5-and-finds-claude-opus-exploiting-a-benchmark-loophole/); [aiweekly](https://aiweekly.co/alerts/openai-drops-swe-bench-verified-backs-pro-after-flaw-audit) (both secondary; figures vary between outlets)
- SWE-bench Pro's own stated limitations (Sep 2025) anticipated two of these: F2P/P2P tests may reject valid alternative solutions, and human augmentation may make requirements overly prescriptive — [SWE-bench Pro paper](https://arxiv.org/html/2509.16941v1)
- SWE-rebench reversed its own design: V1 (2025) chose non-interactive LLM recipes over agents on cost grounds; V2 (2026) reports the non-interactive pipeline at 12.1% pass@1 against 25.8% for the agent and adopted the agent. V1 also showed the contamination gap: DeepSeek-V3-0324 scored 39.7% on SWE-bench Verified versus 21.3% on fresh SWE-rebench tasks — [SWE-rebench V2](https://arxiv.org/html/2602.23866v1); [SWE-rebench V1](https://arxiv.org/html/2505.20411v2)
- SWE-rebench V2 lessons: C/C++ needs explicit rebuilds or tests run stale binaries; Scala needs XML reports because stdout ordering varies; JUnit XML preferred for structured results; regex test-file detection misses inline tests; more than 32k context sometimes causes setup-agent loops; the authors state they ran no training ablation on filtered subsets and support only single-container projects — [SWE-rebench V2 paper](https://arxiv.org/html/2602.23866v1)
- SWE-Universe lessons: agents asked to produce a passing verifier write shallow string-matching checks (4-7 points of apparent success); residual problems after all checks include ambiguous descriptions, environments not matching requirements, and tests misaligned with descriptions — [SWE-Universe paper](https://arxiv.org/html/2602.02361v1)
- SWE-Factory lesson: LLM-written scripts ignore instructions in ways that corrupt grading (`set -e` before the exit-code marker) — [SWE-Factory paper v3](https://arxiv.org/html/2506.10954v3)
- SWE-Gym and SWE-smith lessons on manual effort and storage: about 200 human hours for 11 repos and 6 TB of images (SWE-Gym); R2E-Gym calls its install step semi-manual and hard to scale; SWE-smith still needed about 18 hours of human install review for 128 repos — [SWE-Gym](https://arxiv.org/html/2412.21139v2); [R2E-Gym](https://arxiv.org/html/2504.07164v1); [SWE-smith](https://arxiv.org/html/2504.21798v2)
- SWE-bench-Live (2025): top agent scored 19.25% versus 43.20% on SWE-bench Verified under the same setup, which the authors attribute to freshness; the paper documents only the initial release and a planned monthly cadence — [SWE-bench-Live paper](https://arxiv.org/html/2505.23419v2)
- Internal inconsistencies in the papers themselves: R2E-Gym gives 4,578 and 4,538 for the same subset and "over 33 times" where the ratio is about 3.3; SWE-bench Pro's text and table disagree on two model scores; SWE-Factory per-language counts do not reconcile — [R2E-Gym](https://arxiv.org/html/2504.07164v1); [SWE-bench Pro](https://arxiv.org/html/2509.16941v1); [SWE-Factory](https://arxiv.org/html/2506.10954v3)

### Inferences
- The failure pattern across Verified and Pro is identical and survives heavy human review: tests encode details (names, extra behaviours from the same PR) absent from the task statement, or statements over-specify details the tests do not check. Fleet's fail-to-pass gate measures that the reference fix flips tests; it does not measure whether the statement is sufficient for a different correct fix to pass. That is the largest gap a "measured runs decide" design leaves open, and the only published automated mitigations are interface/naming hints (rebench V2, Pro) and diagnostic labels.
- Container hygiene is a documented attack surface: retained git history, future commits and package versions newer than the base commit. These are deterministic checks.
- If Fleet ever lets an agent write test commands or verifiers, the SWE-Universe and SWE-Factory results say to treat the verifier as untrusted output and check it deterministically (per-test status required, marker presence, no source grepping).
- Benchmarks built from public repos have a short useful life; the systems that persist (SWE-rebench, SWE-bench-Live) are continuous pipelines with date-stamped tasks rather than fixed sets.

### Gaps
- OpenAI's February and July 2026 posts could not be read directly (403); exact wording, sample sizes for the July Pro audit, and whether the Pro recommendation was formally withdrawn are unverified.
- Datacurve's original post was not read; the git-history leak figures are from secondary outlets and differ between them.
- No published post-mortem was found for SWE-Gym, R2E-Gym, SWE-Flow, SWE-Synth or Commit0 being retired or corrected; no information on whether SWE-bench-Live's monthly updates continued through 2026.
- No Scale AI response to the Pro audits was found.
