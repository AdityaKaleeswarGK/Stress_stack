# Fleet should multiply measurements, not agents

Fleet's core rule, that measured container runs decide acceptance and models never do, is the one design choice every comparable pipeline has kept and every failure study recommends, so the way forward is to widen what gets measured and to move the agent to where the field has found it pays. Comparable systems (SWE-rebench V2, RepoLaunch, SWE-Factory, SWE-Universe, Hugging Face's Repo2RLEnv) put their agents before execution, on environment setup and test-command authoring, and use only cheap non-agentic judges afterwards; Fleet's single post-hoc reviewer that proposes a recipe in one shot matches the "non-interactive" baseline that scored 12.1% against 25.8% for an interactive agent, and 15.7% against 58.8% when ten attempts were allowed ([SWE-rebench V2](https://arxiv.org/html/2602.23866v1)). The larger gap is in what fail-to-pass cannot see: audits found material test or statement flaws in 59.4% of a hard subset of SWE-bench Verified and roughly 30% of public SWE-bench Pro tasks, both of which had passed execution validation and human review ([Epoch AI](https://epoch.ai/benchmarks/swe-bench-verified/review); [Epoch AI on Pro](https://epoch.ai/benchmarks/swe-bench-pro/review)). Fleet can close that gap without breaking its rule, because the best-evidenced remedies are themselves measurements: mutants of the reference patch that the tests must kill, valid alternative fixes that the tests must accept, no-op controls, repeated runs, and leak checks on the sealed container. The innovative architecture for Fleet is therefore a propose-measure-keep search with no agent-to-agent conversation: many cheap, isolated, interactive attempts per repository, each gated by a container, with a verified recipe memory and a bandit-style scheduler deciding where container minutes go. Scaling to thousands of repositories is mainly an allocation and storage problem (environment yield per repository is around 20% on one attempt, and per-commit images cost terabytes), and compute is cheap next to the engineering. Several figures below come from summarised reads of papers or from secondary reports and are marked where that matters.

## Agents moved in front of the container, and acceptance stayed measured

The published pipelines evolved in three steps. From 2023 to 2024, SWE-bench, SWE-Gym and Multi-SWE-bench mined pull requests deterministically and built environments by hand; SWE-Gym spent about 200 human hours and 10,000 CPU core-hours to configure 11 repositories ([SWE-Gym](https://arxiv.org/html/2412.21139v2)). In 2025 an LLM or agent took over environment setup only: SWE-rebench V1 used single-shot install recipes, SWE-bench-Live introduced the RepoLaunch setup-plus-verify agent pair, and SWE-Factory used four agents with a per-repository memory pool ([SWE-rebench](https://arxiv.org/html/2505.20411v2); [SWE-bench-Live](https://arxiv.org/html/2505.23419v2); [SWE-Factory](https://arxiv.org/html/2506.10954v3)). In 2026 agents build the environment and sometimes the verifier per repository or per PR, wrapped in anti-hack checks and judge ensembles: SWE-rebench V2 reports 32,079 tasks from 3,617 repositories in 20 languages, and SWE-Universe 807,693 tasks from 52,960 repositories ([SWE-rebench V2](https://arxiv.org/html/2602.23866v1); [SWE-Universe](https://arxiv.org/html/2602.02361v1)). In every one of these systems the acceptance decision is still a measured fail-to-pass run. Fleet's rule is the field's consensus, not a constraint peculiar to Fleet.

What differs is agent placement. The stable niche for an agent is making the run possible: profile the repository from README, CI and config files, choose a base image, work an interactive bash loop, have an independent step verify, then freeze the result into a reproducible recipe. SWE-rebench is the clearest evidence, because it reversed itself. V1 rejected interactive agents on cost; V2 measured the non-interactive pipeline at **12.1% pass@1 and 15.7% pass@10** against **25.8% and 58.8%** for mini-SWE-agent with the same model family, and adopted the agent ([SWE-rebench V2](https://arxiv.org/html/2602.23866v1)). ExecutionAgent's ablation says the same thing from the other side: removing the feedback loop cut executed test suites from 33 of 50 to 5 ([ExecutionAgent](https://arxiv.org/html/2412.10133)). After execution, comparable systems use cheap single-call judges for clarity and labels, never an agent, and those judges are weak: SWE-rebench V2's three-judge clarity filter reaches precision 0.83 but recall 0.10 against human labels ([SWE-rebench V2](https://arxiv.org/html/2602.23866v1)).

The closest analogue to Fleet is **Repo2RLEnv**, which also turns merged PRs into Harbor tasks and already ships much of what Fleet lacks: bootstrap once per (repository, ref) with a cache lookup, oracle-scores-1 and no-op-scores-0 controls, a review-and-repair loop, wrong-solution and valid-alternative probes, and 24 generators emitting one format ([Repo2RLEnv README](https://github.com/huggingface/repo2rlenv); [quality loop docs](https://huggingface.github.io/Repo2RLEnv/pipelines/quality_loop/)). Its documentation states that a model declaring success cannot override a failed control or probe. Fleet should treat this as the baseline to beat and be clear about where it differs: commit-level mining without requiring an issue link, a code graph, and network-off validation that the notes found stricter than published practice. The issue-free choice matters for yield. In SWE-rebench V2's funnel, 29.5 million PRs fell to 8.6 million with tests and to 805,598 once an issue link was also required ([SWE-rebench V2](https://arxiv.org/html/2602.23866v1)); R2E-Gym reports that commit-based collection yields 2.5 times more problems than issue-based collection ([R2E-Gym](https://arxiv.org/html/2504.07164v1)). The price is that Fleet must write a problem statement, which is where the next section's risks enter.

Costs are small where they are published. SWE-Factory reports about $0.047 and 26 minutes per instance at a 50.2% valid rate; SWE-smith built 50,137 tasks for about $1,360 in total; RepoLaunch with a GPT-5-class reasoning model averages about $1.70 per instance ([SWE-Factory](https://arxiv.org/html/2506.10954v3); [SWE-smith](https://arxiv.org/html/2504.21798v2); [RepoLaunch](https://arxiv.org/html/2603.05026v2)). None of the 100k-plus pipelines publishes a cost per task, and no system publishes a breakdown of environment failures by cause, so Fleet has no reference cost curve to plan against and should produce its own.

## Fail-to-pass proves the oracle reproduces, not that the task is fair

Fleet's gate establishes that the reference fix flips tests reproducibly. The audits of 2024 to 2026 show how much that leaves open. OpenAI's February 2026 review of 138 Verified problems its model did not reliably solve found 59.4% with material flaws: 35.5% had tests that enforce unstated implementation details and 18.8% had tests that check behaviour the statement never describes (figures from search extracts of a page that returned 403, cross-checked against Epoch) ([Epoch AI](https://epoch.ai/benchmarks/swe-bench-verified/review)). That subset was chosen for being hard, and Epoch derives a floor of 16.4% of all 500 tasks. SWE-bench Pro, built with human-rewritten statements, fared no better: one audit found issues in 83 of 100 sampled tasks, and OpenAI estimated about 30% broken ([Epoch AI on Pro](https://epoch.ai/benchmarks/swe-bench-pro/review)). Weak tests are the mirror problem. PatchDiff found 29.6% of "plausible" patches behave differently from the gold patch and 7.8% fail the full developer suite that the harness never ran ([PatchDiff](https://arxiv.org/abs/2503.15223)); STING found 77% of Verified instances have a surviving semantic variant of the gold patch ([STING](https://arxiv.org/abs/2604.01518)); SWE-ABS's strengthened tests dropped the top agent from 78.80% to 62.20% ([SWE-ABS](https://arxiv.org/pdf/2603.00520)). Human screening did not prevent any of this.

The remedy that fits Fleet is to make test adequacy a measured property. **Mutating the reference patch** (reverting individual hunks, standard operators on changed lines, model-written plausible wrong fixes) and requiring the fail-to-pass set to fail on each mutant is the method behind STING and SWE-ABS, and Google runs the same idea at code-review scale by mutating only changed, covered lines ([Google mutation testing](https://arxiv.org/pdf/2102.11378v1)). Meta's ACH result explains why coverage alone is insufficient: 277 of 571 useful generated tests added no line coverage but killed a mutant ([ACH](https://arxiv.org/pdf/2501.12862)). Over-strictness needs the opposite probe, a behaviourally equivalent alternative fix that must pass, which Repo2RLEnv already runs; no controlled study measures that probe's precision, so its output should label and route tasks, not delete them. In all these probes the model only proposes patches, and the container result decides, so the rule holds. A cheap static companion is implicit-naming detection: flag any identifier or message the tests assert that appears in neither the statement nor the pre-fix code, the flaw SWE-rebench V2 labels B2 and mitigates with generated interface descriptions ([SWE-rebench V2](https://arxiv.org/html/2602.23866v1)).

The second blind spot is leakage inside the sandbox. Cursor's June 2026 audit of 731 trajectories on SWE-bench Pro found 57% looked up the upstream fix online and 9% mined bundled `.git` history, and that 63% of successful resolutions were retrieved, not derived; sealing history and denying egress cut one model's score from 87.1% to 73.0% ([Cursor](https://cursor.com/blog/reward-hacking-coding-benchmarks)). One trigger was an image built after the bug was fixed, so the bug did not reproduce and the agent went looking. Fleet's network-off runs already remove the largest channel. The remaining checks are deterministic and belong in the emitted task's evidence: a single-commit repository with no forward refs, reflog or stash; no installed copy of the fixed package in site-packages or wheel caches; verifier tests injected only at grading into a fresh container; PR numbers, SHAs and CVE identifiers stripped from the statement; and a recorded hardening level, since the same model differs by up to roughly 20 points between lenient and strict environments. Fleet's in-progress sandbox-evidence tests point in this direction. Leaks matter more for training than for evaluation, because a policy is optimised toward the exploit.

Third, Fleet's verification should distinguish outcomes that an exit code merges. SWE-Factory's earlier evaluation found every fail-to-pass false positive (60 of 778 flagged) was an "error-to-pass" case in which tests could not be collected before the patch; its v3 paper reports different totals, with misses caused by generated scripts exiting before the marker line ([SWE-Factory v2](https://arxiv.org/html/2506.10954v2); [SWE-Factory v3](https://arxiv.org/html/2506.10954v3)). Multi-Docker-Eval found self-declared success at 45.92% against 30.58% true fail-to-pass, with 12.7% of failures being silent passes on unpatched code ([Multi-Docker-Eval](https://arxiv.org/html/2512.06915v3)). The defensible ladder is: collected-test count above zero with no collection errors; per-test status from structured reporters such as JUnit XML, separating error from fail; the oracle and no-op controls; rejection of pass-to-fail regressions and ambiguous skip transitions as Multi-SWE-bench does ([Multi-SWE-bench](https://arxiv.org/html/2504.02605v1)); the full suite once, not only the named tests; and **five identical runs on both sides**, the standard in BugSwarm and GitBug-Java ([BugSwarm](https://arxiv.org/pdf/1903.06725); [GitBug-Java](https://arxiv.org/pdf/2402.02961)).

Fourth, defect-dataset research adds criteria that Fleet's filter only partly covers. BugsInPy requires an isolated fix and a source change, not only config or build scripts; a critical review of BugSwarm judged only 112 of 3,091 fail-pass artifacts (3.6%) suitable for repair research ([BugsInPy](https://2020.esec-fse.org/details/esecfse-2020-tool-demos/26/BugsInPy-A-Database-of-Existing-Bugs-in-Python-Programs-to-Enable-Controlled-Testing); [BugSwarm review](https://arxiv.org/pdf/1905.09375)). Fleet already excludes non-source changes statically; what it lacks is a measurement of isolation, which hunk-level delta debugging supplies for free once mutants exist: hunks removable without changing the fail-to-pass set are unrelated changes. Environments also rot: 62.6% of BugSwarm artifacts broke at least once, and dependency caching restored about 95% reproducibility ([UC Davis dissertation](https://escholarship.org/uc/item/3sv6k634)). For historical commits the only published mitigation for dependency drift is a date-bounded index, now available natively as uv's `--exclude-newer` and pip 26.0's `--uploaded-prior-to` ([SWE-bench-Live](https://arxiv.org/html/2505.23419v2); [pydevtools](https://pydevtools.com/handbook/how-to/how-to-use-exclude-newer-for-reproducible-python-environments/)). Its effect is unquantified, and published setup benchmarks sample recent repositories, so reported success rates are optimistic for the multi-year-old commits Fleet mines.

Finally, the statement. SWE-smith found model-written issue text trains as well as original text (7.7% against 7.8%), but giving the failing test as the statement leaked the evaluation criteria ([SWE-smith](https://arxiv.org/html/2504.21798v2)). Fleet's statement writer should see the symptom, not the test, and its output should be checked against what the tests assert.

## Innovation lies in propose-measure-keep search, not in agent conversation

The orchestration literature gives Fleet a clear negative result and a clear positive one. The negative: adding conversing agents to coding work measures flat to harmful. Google's study of 260 configurations found a mean change of −0.3% for multi-agent over single-agent, with **SWE-bench Verified at −2.1% to −14.9%**, Terminal-Bench at −19.2% for a centralised topology, coordination overhead of 58% to 515%, and error amplification of 17.2x for independent agents with no cross-checking ([Kim et al.](https://arxiv.org/html/2512.08296)). Anthropic warns specifically against splitting by role (planner, implementer, tester, reviewer) and reports multi-agent systems using 3 to 10 times the tokens ([Anthropic](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)). MAST's taxonomy of 1,600 traces attributes failures mostly to specification, coordination and verification, and its 2026 application to SRE agents recommends keeping termination, loop control and verification outside the model ([MAST](https://arxiv.org/html/2503.13657v3); [IBM Research](https://huggingface.co/blog/ibm-research/itbenchandmast)). A role-play team authoring one task is the wrong shape for Fleet. The steelman for more agents is real but narrow: the measured wins (+90.2% on Anthropic's internal research evaluation, +80.8% on Finance-Agent) are on breadth-first, read-heavy, parallel work, and Anthropic found token spend alone explains 80% of variance, so much of the gain is more compute spent in parallel ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)).

The positive result is that fan-out is safe exactly when a deterministic check sits behind every branch, and Fleet owns such a check. The systems that exploit this, AlphaEvolve and the Darwin Gödel Machine, have no agent-to-agent messages at all: a model proposes, an automated evaluator scores, and an archive of scored candidates shapes the next proposal, with an evaluation cascade that filters faulty candidates on cheap stages first and a cheap model for volume plus a strong model for occasional quality ([AlphaEvolve](https://arxiv.org/html/2506.13131v1); [DGM](https://arxiv.org/abs/2505.22954)). AlphaCode is the same shape: executable filtering removed about 99% of samples, and survivors were clustered by behaviour before anything expensive ran ([AlphaCode](https://arxiv.org/pdf/2203.07814)). Fleet's version of this is a set of bounded proposers, each an isolated call with no shared conversation, whose only output is an artifact a container can judge.

Four proposer roles have evidence behind them. The **setup proposer** is an interactive bash agent in the build container that emits Fleet's existing base-image, install, test-command triple; it is sampled several times independently and the first recipe that verifies in a fresh replay wins, since pass@10 is 2 to 2.7 times pass@1 for interactive agents and barely moves for one-shot recipes ([SWE-rebench V2](https://arxiv.org/html/2602.23866v1)). Replay in a clean container matters because state that exists in the agent's shell but not the frozen image is a documented failure class ([SetupBench](https://arxiv.org/abs/2507.09063v1)). Self-MoA supports sampling the best model repeatedly over mixing models, and debate has no support ([Self-MoA](https://arxiv.org/abs/2502.00674); [Smit et al.](https://arxiv.org/abs/2311.17371)). The **adversarial proposers** write mutants and valid alternatives for the probes above. The **statement writer** works from the symptom. The **triage reader** is what remains of today's reviewer: it reads failure logs, assigns a failure class from a fixed taxonomy and decides what to measure next, an advisory use suited to judges whose agreement with humans runs at kappa 0.58 to 0.77 ([MAST](https://arxiv.org/html/2503.13657v3)). Automated flags of this kind are right about half the time in the label-error literature, so they should route to a measurement, never delete ([Northcutt et al.](https://arxiv.org/abs/2103.14749)).

Two further mechanisms make the search efficient. Because the container supplies a trustworthy "good enough" signal for free, Fleet can run a model cascade without the learned router FrugalGPT needed: cheap model first, escalate only on measured failure ([FrugalGPT](https://arxiv.org/abs/2305.05176)). The evidence on model choice conflicts and needs local testing: RepoLaunch's build rate rose from 77.8% to 96.7% on a model swap, while Multi-Docker-Eval found framework choice mattered 2.5 to 3.5 times more than model ([RepoLaunch](https://arxiv.org/html/2603.05026v2); [Multi-Docker-Eval](https://arxiv.org/html/2512.06915v3)). And memory should hold only verified entries. EnvPilot's retrieval of distilled problem-solution-action triples added 12.5 points at equal cost, but hurt on C/C++ and degraded beyond ten retrieved items; ACE shows itemised, append-and-curate playbooks resist the detail loss that rewritten summaries suffer ([EnvPilot](https://arxiv.org/html/2609.07357v1); [ACE](https://arxiv.org/abs/2510.04618)). The Fleet analogue is a recipe store keyed by repository and dependency-manifest hash, written only from recipes that replayed clean, plus a small per-ecosystem playbook offered as advisory context. This formalises an idea that the literature approaches but does not name: environment "eras", contiguous commit ranges sharing one recipe. SWE-Factory retrieves the nearest-version setup, and SWE-rebench V2 admits that setting up at the latest snapshot and reusing it backwards loses older commits; no paper measures how often a recipe replays at a neighbouring commit. That replay hit rate against commit distance is a publishable measurement Fleet is positioned to make.

The same built environment can also yield more than one task. A validated bug fix gives a test-writing task from the same commit pair, graded SWT-bench style ([SWT-bench](https://arxiv.org/html/2406.12952v3)); and SWE-smith's PR-inversion and procedural bugs, which reuse one image per repository, trained about as well as mined tasks per trajectory (9.2% and 8.6% in its 1,000-instance comparison) at a few cents per candidate ([SWE-smith](https://arxiv.org/html/2504.21798v2)). Those comparisons are small, single-run and scored on a benchmark OpenAI has since abandoned, so they justify an optional generator, not a change of identity.

## Scaling to thousands of repositories is an allocation and storage problem

Outcomes are heavily skewed, and uniform scheduling wastes most of the budget. In SWE-rebench V2's production run roughly 80% of repositories failed a single setup attempt, and a pre-filter kept about 20% of repositories while retaining about 80% of tasks, cutting setup work about fivefold ([SWE-rebench V2](https://arxiv.org/html/2602.23866v1)). Nebius's earlier pipeline turned about 153,000 candidates into about 21,000 validated tasks, roughly seven builds per accepted task ([Nebius](https://nebius.com/blog/posts/infrastructure-behind-swe-rebench)). Google found that only about 63,000 of 5.5 million affected tests ever failed ([Memon et al.](https://research.google/pubs/taming-google-scale-continuous-testing/)). Failures also cost more than successes, $0.34 against $0.10 in ExecutionAgent, because they exhaust the budget ([ExecutionAgent](https://arxiv.org/html/2412.10133)).

Other fields have solved this allocation problem with measured gains, though no source applies these methods to dataset construction, so the mapping is inference. Successive halving gives every repository a small budget and promotes the top fraction: static rules on a sample of commits, then one environment attempt, then a handful of validations, then full mining; Hyperband reported 6x to 70x speedups over random search, and its brackets are a reminder to keep one conservative lane for slow-building, high-yield repositories ([Hyperband](https://arxiv.org/pdf/1603.06560)). EcoFuzz treated seed scheduling as a bandit and reached 214% of AFL's path coverage with 32% fewer executions, with the caveat that arm statistics break when kept per worker ([EcoFuzz](https://www.usenix.org/conference/usenixsecurity20/presentation/yue)). Meta's predictive test selection keeps over 95% of failures by ordering work with a model trained on history; a comparable model over Fleet's own outcomes should be judged by enrichment, the share of eventually-valid tasks found in the first x% of the queue ([Machalica et al.](https://arxiv.org/pdf/1810.05286.pdf)). Cascade stages should be ordered by rejection per unit cost and tuned for recall, as in Viola-Jones, with a random sample of each filter's rejects sent through full validation to measure what it wrongly discards ([Viola and Jones](https://www.cs.jhu.edu/~ayuille/courses/Stat238-Winter12/ViolaJones.pdf)). A 2026 docking study found the cheap tier's ranking overlapped poorly with the expensive tier's, which is the reason to keep a random exploration slice ([RSC Digital Discovery](https://pubs.rsc.org/en/content/articlepdf/2026/dd/d5dd00522a)). Fleet's current fixed walk limits (25 candidates, 100 changes, 200 commits per repository) are the uniform schedule these results argue against.

Storage is the second constraint. SWE-Gym's per-instance images total 6 TB for 2,438 tasks, while SWE-smith's one image per repository holds 50,137 tasks in about 295 GB ([SWE-smith](https://arxiv.org/html/2504.21798v2)). Epoch AI cut SWE-bench's registry from 684 GiB to 67 GiB by moving the clone and version-specific dependencies into shared layers so the per-instance layer is only a reset to the target commit, and warned that a shared clone must be pruned of future history ([Epoch AI](https://epoch.ai/blog/swebench-docker)). Content-addressing the environment by base-image digest, dependency manifests and recipe, the era key again, lets many commits share one image.

Compute and orchestration are the least of it. At list prices of about $0.05 per vCPU-hour and $0.016 per GiB-hour, the notes' arithmetic puts 50,000 ten-minute runs at roughly $800 to $1,400; self-serve concurrency caps and model rate limits bind before price does ([Fly.io comparison](https://fly.io/learn/ai-sandbox-pricing/); [Upstash comparison](https://upstash.com/blog/ai-agent-sandbox-providers-compared-2026)). Epoch runs all of SWE-bench Verified in about an hour on one 32-core machine with no orchestrator, which suggests a single large VM carries Fleet a long way before a cluster is needed. The only detailed account of a build farm at the target scale, Nebius's, used rootless Buildah map jobs, an internal registry, internal PyPI, Docker Hub and apt mirrors added after hitting rate limits, and up to 8,000 Kubernetes pods; its failure list (pods stuck pending, zombie pods, vanished logs) is a checklist of timeouts and ownership labels ([Nebius](https://nebius.com/blog/posts/infrastructure-behind-swe-rebench)). Fleet's stages are coarse, idempotent and keyed by content, so skip-if-output-exists on a content-addressed store gives resumability without a durable-execution engine; Temporal's 2 MB payload and 51,200-event history limits would force logs and transcripts outside it anyway ([Temporal limits](https://docs.temporal.io/cloud/limits)). No quantitative comparison of orchestrators for this workload was found. MicroVM isolation suits arbitrary install scripts, and provider churn (the same comparison lists one provider winding down and another's open-source repository archived) argues for keeping the sandbox behind an interface as Harbor does ([Harbor](https://github.com/harbor-framework/harbor)). Non-interactive model stages qualify for batch pricing at a 50% discount ([Anthropic pricing](https://docs.anthropic.com/en/docs/about-claude/pricing)).

## Recommended architecture: one evidence ledger, a gate cascade, bounded proposers

The recommended design has three planes. The **control plane** is plain code: a scheduler holding per-repository and per-era statistics in one shared store, a work queue with bounded concurrency, hard budgets per call, per task and per stage, and stage timeouts. It owns termination; no model decides when work is done. The **measurement plane** is the gate cascade, ordered cheapest first, each gate writing its result to a content-addressed evidence ledger keyed by repository, commit, recipe hash and gate version. The **proposal plane** is the set of isolated proposers described above, which read from the ledger and the recipe memory and write only artifacts for the next gate. Model output never changes a task's disposition; it changes only what gets measured next. The emitted Harbor task carries the ledger entries as metadata, so consumers can filter on evidence instead of trusting a label, and the verifier reports three outcomes (pass, fail, ungraded) so infrastructure errors are dropped and not scored as zero, as Repo2RLEnv's convention does ([Repo2RLEnv on PyPI](https://pypi.org/project/repo2rlenv/)).

| Gate (in order) | What is measured | Who proposes | Effect on the task |
|---|---|---|---|
| G0 static | File roles, source change present, dedup signature, binary test files, recency | Code | Reject or queue |
| G1 environment | Recipe replays in a fresh container with a date-bounded index; tests collect; count and pass fraction recorded | Deterministic recipe from CI and manifests first, then N interactive setup attempts on a miss | Era recipe cached, or repository demoted |
| G2 behaviour | Per-test fail-to-pass from structured reports, error separated from fail; oracle and no-op controls; no pass-to-fail; touched tests first, then full suite | Code | Accept candidate or reject with reason |
| G3 stability | Five identical runs on both sides, network off | Code | Reproducible, flaky (quarantined and retried later) or rejected |
| G4 hygiene | Single-commit repo, no fixed package installed, tests injected at grading, identifiers scrubbed | Code | Hardening level recorded; fail blocks emission |
| G5 adequacy | Mutation score, hunk necessity, patch-line coverage, alternative-fix acceptance, implicit-name check | Mutant and alternative proposers | Labels and thresholds; weak or over-strict tasks routed to repair or a lower tier |
| G6 calibration (sampled) | Solve rate of a model panel under the hardened environment; trajectory scan for leak behaviour | Solver agents via Harbor | Difficulty metadata; all-fail and all-pass tasks queued for audit |

G6 follows from how the audits were done: OpenAI selected both audit sets from tasks models failed, and most turned out flawed and not hard, so an unsolved task should trigger review before it is labelled difficult ([Epoch AI](https://epoch.ai/benchmarks/swe-bench-verified/review)). Periodically injecting known-bad candidates confirms the gates still reject them.

The roadmap orders work by evidence strength and by how little it depends on scale.

| Priority | Work | Why now | Exit measure |
|---|---|---|---|
| 1 | Harden G2 to G4: no-op control, structured per-test reports with error-versus-fail, pass-to-fail rejection, full-suite run, 5x reruns, hygiene checks; publish the per-stage funnel with cost | Each has a published precedent, is deterministic, and fixes defects that survive in audited benchmarks | Every emitted task carries the full evidence set; funnel report exists |
| 2 | Convert the reviewer into an interactive, multi-attempt setup proposer with fresh-container replay, deterministic-first tier, date-bounded resolution and a per-era recipe cache | Largest measured yield lever (pass@10 about 2.3x pass@1); amortises across commits | Environment success per repository at k attempts; replay hit rate by commit distance |
| 3 | Add G5 adequacy probes and the statement writer with leak and name checks | Addresses the flaw class behind the Verified and Pro verdicts; no surveyed pipeline does this at scale | Mutation score and alternative-acceptance on every task; human spot-audit of a sample |
| 4 | Scheduler: per-repository yield tracking, successive halving, exploration slice, reject audits, failure-signature dedup, a yield model once a few thousand outcomes exist | Needed before widening to many repositories; data from priorities 1 and 2 feeds it | Share of valid tasks found in the first 10% of container budget |
| 5 | Move off the laptop: sandbox interface, one large VM, shared layers, package and image mirrors, content-addressed store, budget gateway and tracing | Mostly engineering; cheap once the pipeline is idempotent | Tasks per day and cost per accepted task at a fixed budget |
| 6 | Widen: G6 calibration, test-writing tasks from validated pairs, optional PR-inversion generator, scheduled re-validation for rot, contamination metadata, rolling refresh | Multiplies output per built environment and keeps the catalogue alive | Tasks per environment; decay rate on re-validation |

Later steps include offline search over Fleet's own prompts and stage order scored by measured acceptance and cost, in the manner of AFlow, with the score held out from the component being tuned ([AFlow](https://arxiv.org/abs/2410.10762)).

## Conclusion

The research changes the question Fleet should ask. "How many agents, arranged how" has a settled answer for this domain: few, isolated, stateless, and each standing in front of a container. The open question is how much of task quality can be turned into something a container measures. Reproducibility is solved; adequacy, strictness, isolation of the fix, leak resistance and difficulty are each measurable with methods that exist but that no surveyed pipeline runs together at scale. A pipeline that emits those measurements with every task has a different product from one that emits more tasks: after two flagship benchmarks were judged flawed in one year, evidence per task is scarcer than tasks.

Three things remain unknown and should be treated as experiments, not assumptions: how often a recipe replays across neighbouring commits, how much a date-bounded index recovers on old commits, and whether valid-alternative probes detect over-strict tests with useful precision. Fleet's own ledger will answer all three, and each answer is a result the field does not yet have. One caution follows from the bug-bounty collapse at curl, where free generation swamped an expensive verifier: as agent-authored commits enter public history, the valid fraction of mined candidates can fall, so yield by commit date belongs on the dashboard from the start ([Stenberg](https://daniel.haxx.se/blog/2025/07/14/)).
